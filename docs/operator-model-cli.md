# Частичная модель и пакет из operator capture

Команды доступны в Node 24 после `operator-capture ingest`. Они принимают **COMMITTED** capture с явно переданным ID и SHA-256 исходного манифеста. Изменяемый каталог оператора после ingest больше не нужен. Исходный автоматический обход остаётся самостоятельным: его артефакт, `PAUSED`, активный access block и readiness не меняются.

```sh
npm run upgrade -- operator model --project PROJECT \
  --capture CAPTURE_ID --manifest-sha256 MANIFEST_SHA256

npm run upgrade -- operator build --project PROJECT \
  --capture CAPTURE_ID --manifest-sha256 MANIFEST_SHA256 --model MODEL_ID

npm run upgrade -- report --project PROJECT
```

При нескольких наблюдавшихся URL `operator model` требует `--page ABSOLUTE_URL`. В первой версии каждый пакет содержит ровно одну явно выбранную наблюдавшуюся страницу. `operator build` использует выбор принятой модели; переданный `--page` обязан совпадать. Общий каталог состояния задаётся обычным `--data-dir PATH` или `UPGRADE_DATA_DIR`. Идентификатор модели — поле `id` JSON-ответа первой команды. Ответ сборки содержит `package_dir`, `manifest_sha256_package`, `result_artifact_id` и `runtime_verification: NOT_RUN`.

## Контракты и полнота

`operator_model` и `operator_build` — отдельные сохраняемые записи Store со состояниями `PENDING` и `COMMITTED`. Они не заменяют обычные stages `extract`/`build`, crawl result или content-model. Все производные артефакты имеют `state: PARTIAL`, `full_source_denominator: UNKNOWN`, `input_hash` и одинаковую `operator_binding`: project, capture ID/manifest SHA, принятый capture result ID/SHA, исходный crawl ID/SHA, наследуемый access block и выбранный source URL.

| Артефакт                         | Содержание                                                                                               |
| -------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `operator-content-model.json`    | Одна сущность, наблюдения и доказательства, полный source inventory, проверенные ссылки на файлы capture |
| `operator-route-manifest.json`   | Не более одного точного пути; остальные URL unresolved, запрещённые пути — conflicts                     |
| `operator-scope-manifest.json`   | Весь известный реестр, число выбранных/запланированных/нерешённых URL; полный размер сайта UNKNOWN       |
| `operator-release-manifest.json` | Пин локального пакета, ссылки на модель/routes/scope и наследуемая привязка capture                      |

URL сохраняет регистр, процентное кодирование, порядок, повторы и пустые значения query. `expected_status: 200` означает **планируемый ответ частичной целевой страницы**, а не измеренный HTTP-статус источника. Редиректы и canonical по выбранным полям не изобретаются. Пути собственных расширений и Битрикс не получают исполняемых маршрутов. Неизвестные URL не исключаются из знаменателя: для fixture 25 известных URL результат — 1 маршрут и 24 нерешённых, полный размер сайта неизвестен.

Выбранные поля остаются точными текстовыми наблюдениями с locator, timestamp и SHA доказательства. В V1 тексты нескольких цен и наличия не превращаются в нормализованные цены, предложения или складские остатки: `prices`/`offers` пусты, соответствующие факты UNKNOWN. Product допускается чистым extractor только по однозначной структуре schema.org, связанной с той же страницей; коммерческая семантика всё равно требует отдельной проверки. Исходный текст никогда не становится инструкцией или исполняемым PHP.

## Проверка байтов и повтор

Каждый вход сначала проходит `Store.validateArtifact`, затем читается ограниченно через дескриптор с повторной проверкой размера, inode и SHA. Extractor получает именно эти проверенные байты через resolver. Исходный manifest также проверяется по схеме и по принятому пину. Незавершённый, чужой, повреждённый capture или конфликтующий ID/SHA отклоняется до производных публикаций. Привязка берётся из принятого capture, а не из самого нового crawl: позднее исследование не переопределяет прежние доказательства.

Модель хранит media SHA/size/mime и относительный `operator_file`; абсолютные пути источника не сохраняются. Перед сборкой файлы материализуются из артефактов в собственный `operator-media/`, их содержимое и подпись проверяет также существующий Bitrix builder. Временный compatibility status `FETCHED` применяется только внутри вызова builder и означает готовые локальные байты; сохранённая модель по-прежнему помечает source access как NOT_VERIFIED. Недостающие изображения/документы не загружаются по сети и сохраняют блокеры builder. Пакет с блокерами не считается пригодным для импорта.

Input ID вычисляется из пинов входа и fingerprint исполняемого кода. До публикации сохраняется намерение и SHA выходов. После неизвестного результата записи повтор ищет уже зарегистрированный артефакт с тем же типом и SHA и проверяет его байты. Неполная попытка сборки остаётся отдельно в `operator-builds/`; только проверенный подготовленный manifest получает сохраняемый пин, после чего каталог атомарно перемещается в `operator-releases/`. COMMITTED повтор проверяет исходные доказательства, результат и весь пакет; повреждение не исправляется молча. Изменившаяся во время вычисления реализация отклоняется.

Блокировка dispatcher ограничивает запись одним процессом. Команда использует maintenance lease, поэтому работает при PAUSED без снятия source gate. Пределы исходного capture: 200 MB суммарно, 20 MB на payload, 10 000 URL, 1 000 наблюдений и 5 000 assets. Отдельного CLI wall-time флага в этом пути нет. Неиндексированный файловый остаток после аварии между записью файла и его регистрацией не принимается как результат; это общая граница существующего artifact Store.

Пакет использует собственный Bitrix builder и шаблон. Его manifest содержит явные partial warnings, `data/operator-scope.json` содержит полный известный реестр, а шапка показывает «Частичный снимок … 1 из N известных URL … Полнота источника не установлена». Сборка не обращается к целевой БД и не запускает PHP Битрикс. Обычные команды `extract`, `build`, `import`, `verify` и readiness gates не обходятся. Для отдельного импорта частичного пакета необходимы явный согласованный scope, проверка manifest/его blockers и существующий шлюз единственного писателя в изолированную БД; данная команда его не вызывает.

## Фактическая проверка

`node --disable-warning=ExperimentalWarning --test tests/e2e/operator-model.test.ts` — 6/6 PASS. Первый тест запускает настоящие CLI subprocess: ingest → model → build → report → repeat → backup → restore → repeat. В каждом subprocess сетевые API/DNS/socket защищены tripwire; попытка обращения даёт отдельный провал. Исходный capture и каталог проекта переименованы до повторов, а восстановленный пакет использует новый путь и прежние пины. Проверены 25/1/24, исходный PAUSED/block, raw цены/наличие, точный URL и query, media bytes, отдельные report counts и сохранение NOT_READY. Прочие тесты проверяют неизвестный результат публикации модели/пакета, изменение latest crawl, неверный pin, повреждённые media/package и конфликт служебного пути.

`npm run check` — PASS. Настоящий импорт, браузерные сценарии и HTTP Битрикс этим набором не проверяются: **NOT_RUN**. Backup/restore в тесте относится к состоянию Upgrade, а не к БД/файлам установленной CMS.
