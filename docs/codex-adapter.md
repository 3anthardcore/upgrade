# Исполняемая команда Codex

Адаптер использует документированный внешний процесс [Codex CLI, non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode). Внутренние инструменты приложения Codex, клики по чату и скрытые API не используются. Проверены Node.js 24.20.0 и Codex CLI 0.154.0; среда развёртывания проекта требует Node.js 24.x. Node.js 22.13 не поддерживает принятый здесь запуск TypeScript и SQLite.

`packages/codex-adapter/index.ts` реализует `probe`, `start`, `poll`, `cancel`, `collectResult`. `CodexDispatcher.execute` использует публичные операции `Store`, сохраняет задачи до запуска, резервирует бюджет, получает lease, поддерживает heartbeat и публикует результаты через ядро. Одновременно допускаются максимум три задачи без пересечения областей результатов. Исполнители не получают прямой доступ к SQLite. Авторский результат остаётся `VALIDATING`; отдельный проверяющий вызывает `acceptTask` после фактических проверок.

`agents/*.md` загружаются адаптером по `task.role`, входят в фактический промпт и хешируются. Все десять ролей доступны одному механизму исполнения. Текущий профиль агента ограничен структурированными результатами **без инструментов**. Предложения кода и дизайна требуют отдельной проверки и применения; роли разработчиков сами не меняют файлы. Это не доказательство автономной работы всех этапов миграции.

## Запуск

Установить Codex CLI, выполнить штатную авторизацию в аккаунте оператора и проверить `codex --version`. Авторизация и модель сервера настраиваются отдельно; доступность сессии настольного Codex не означает, что CLI сервера авторизован. Подписка Codex не считается API-балансом. Секреты в репозиторий, YAML, журналы и промпты не записываются.

```bash
export UPGRADE_CODEX_MODEL='<доступная-модель>'
npm run test:agents
```

Если переменная модели отсутствует, тест извлекает только поле `model` из конфигурации установленного CLI (`CODEX_HOME/config.toml`, иначе `~/.codex/config.toml`). Имя модели в коде отсутствует. Сам адаптер всегда требует явную модель. `UPGRADE_CODEX_BIN` позволяет задать путь к исполняемому Codex или `codex.js`; shell-обёртки `.cmd`, `.bat`, `.ps1` отвергаются. Без override ищется native binary или штатный npm entrypoint. Команды запускаются `spawn` с массивом аргументов и `shell:false`; промпт передаётся через stdin.

`probe` проверяет версию и необходимые flags установленной сборки, но не проверяет авторизацию, лимиты или доступность модели. Их проверяет реальный запуск. Используются `exec --json --output-schema --output-last-message --sandbox read-only --cd --ignore-user-config --ephemeral`, явная модель и отключение shell, приложений, браузера, web search, plugins/hooks, memory и вложенных агентов. Обнаруженное событие вызова инструмента завершает задачу ошибкой политики; это дополнительный контроль, а не разрешение побочных эффектов. Перед расширением профиля инструментов нужна отдельная проверка изоляции.

## Сохранение и восстановление

Рабочий процесс получает отдельный каталог `agent-jobs/job-UUID/`: `job.json`, `prompt.txt`, `result.schema.json`, `events.jsonl`, `result.json`. Фиксируются версия CLI, модель, роль, workspace, prompt hash, role hash, время, PID, статус и доступные токены. Reasoning, полный stderr, тексты команд и содержимое сообщений не попадают в события. Полезный итог хранится только как отдельный результат по схеме. Денежная стоимость `UNAVAILABLE`, а не ноль.

Отдельный локальный `worker.ts` сохраняет итог даже при закрытии породившего CLI. Повторный экземпляр адаптера читает те же job IDs без новой генерации. Это явно запущенный процесс; работа после выключения хоста не обещается. Отмена создаёт файл запроса; worker останавливает дерево через process group в Linux либо `taskkill /T /F` в Windows. Лимит времени не больше пяти минут на задачу, максимум 256 KiB входных артефактов и 2 MiB событий/диагностики.

Dispatcher проверяет сохранённый CANCELLED/FAILED и владение при каждом цикле ожидания (200 мс), запрашивает остановку активных дочерних процессов и прекращает публикацию. `cancelPersistedJobs(projectAgentJobsDirectory)` доступен после перезапуска CLI без установленного/авторизованного Codex: он пишет cancellation requests в известные job-каталоги и возвращает IDs/ошибки. Фактические subprocess-тесты проверяют остановку после persisted cancellation и после CANCELLED в Store, отсутствие опубликованных артефактов. Если worker погиб и не может обработать файл отмены, подтверждённая остановка не заявляется: сохраняется UNKNOWN и требуется сверка.

При гибели worker или хоста незавершённый статус после timeout + 15 секунд становится `UNKNOWN`, сохраняется `reconciliation-required.json`. Автоматический повтор неизвестного задания отсутствует. Сначала оператор/ядро сверяют итоговый файл, схему, job ID, входные хеши, актуальный lease и расход. Истёкший lease не получает права публикации от наличия файла. Повторная приёмка через старый dispatcher после истёкшего lease не реализована; требуется новый контролируемый attempt ядра после сверки. Поиск старого PID не считается достаточным основанием для убийства чужого процесса.
