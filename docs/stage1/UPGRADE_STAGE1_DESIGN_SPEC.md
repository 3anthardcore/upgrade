# Upgrade ТЗ на сервис генерации дизайна сайта по ссылке

Дата: 1 октября 2026 года. Версия: 1.0.

Задача этого этапа — создать веб-сервис, в котором пользователь вставляет ссылку на существующий сайт, а ИИ изучает его и показывает новый дизайн в виде готовой картинки. Основной результат разработки — работающий путь от ссылки до индивидуального изображения, доступного для просмотра и скачивания.

Документ самостоятельный. Прежнее ТЗ на перенос сайтов в Битрикс не является заданием для этого этапа. Здесь описаны требования к будущему сервису, а не уже реализованные возможности.

## 1 Результат первой версии

Основной сценарий:

**Ссылка → изучение сайта → краткий анализ → новый дизайн → проверка картинки → показ пользователю.**

Принятое для первой версии допущение: один запуск создаёт один дизайн главной страницы для компьютера, целиком в одной вертикальной картинке. Это новая композиция главной с необходимыми блоками, а не обязательное повторение всех секций исходника. Мобильный дизайн и внутренние страницы можно добавить следующим этапом.

Пользователь получает:

- Скриншот исходной главной страницы с датой получения.
- Краткое описание бизнеса и 3–5 конкретных замечаний к существующему оформлению.
- Одну готовую картинку нового дизайна главной страницы.
- Краткое объяснение основных изменений.
- Возможность увеличить изображение, скачать PNG и попросить правку текстом.

Выдаваемый результат обозначается как «Концепция дизайна». Разработка работающего сайта, перенос страниц, Битрикс, сохранение маршрутов, SEO-миграция и подключение форм в этот этап не входят. Также не требуются тарифы, оплата, CRM, массовая рассылка или сложная система управления агентами.

## 2 Сценарий пользователя и интерфейс

Сервис должен быть доступен через браузер. Пользователю не требуется открывать Codex, запускать команды или самостоятельно составлять промпты.

### Экран создания дизайна

Обязательные элементы:

- Поле «Ссылка на сайт».
- Необязательное поле «Что хочется изменить».
- Необязательный выбор направления: «Подобрать автоматически», «Лаконичный», «Выразительный», «Премиальный».
- Кнопка «Создать новый дизайн».
- Короткое пояснение: «Изучим сайт и подготовим концепцию главной страницы в виде изображения».

Значение по умолчанию — автоматический подбор. Не заставлять пользователя заполнять большой бриф, выбирать модель или разбираться в технических параметрах.

Если введена ссылка на внутреннюю страницу, интерфейс до запуска показывает найденную главную и объясняет, что дизайн создаётся для неё. Нельзя молча заменить отдельный сайт в подкаталоге или поддомене другим сайтом. Если главную определить неоднозначно, уточнить адрес в интерфейсе.

### Экран выполнения

Показывать фактический текущий шаг:

1. Открываем сайт.
2. Изучаем бизнес и оформление.
3. Создаём новый дизайн.
4. Проверяем изображение.

Не показывать выдуманный процент готовности. Страница может обновляться без потери задания. Повторное нажатие кнопки при сетевом сбое не должно создавать несколько платных генераций.

### Экран результата

Главное место занимает новое изображение. Рядом или во вкладке доступен исходный скриншот. Изображения длинных страниц просматриваются независимо, без растягивания одной под высоту другой.

Ниже разместить короткий анализ и список изменений. Доступны кнопки «Скачать PNG» и «Внести правку», поле текста правки и список сохранённых версий текущего результата. Первая версия остаётся доступной после создания следующей.

Пример правки: «Сделай оформление светлее, увеличь фотографии товаров и сохрани текущую структуру». Сервис учитывает предыдущую картинку и меняет запрошенные части, сохраняя факты о компании.

## 3 Как сервис изучает сайт

Вход может вести на сайт любой CMS или самописной платформы. Определение CMS не требуется для создания картинки.

Браузерный инструмент открывает главную, ждёт появления основного содержимого, делает ограниченную прокрутку для загрузки изображений и сохраняет скриншот. Тексты и ссылки извлекаются из DOM. Визуальная модель получает скриншоты, а не только название домена.

Для понимания бизнеса разрешено изучить до четырёх дополнительных публичных страниц: например, «О компании», услуги, каталог и контакты. Максимум пять HTML-страниц за один анализ. Полный обход всех товаров и ссылок не нужен.

Извлечь, если присутствует:

- Название компании и логотип.
- Сферу деятельности, основные товары или услуги.
- Главное предложение и предполагаемое целевое действие посетителя.
- Географию работы, язык и контакты.
- Основные разделы меню.
- Фотографии и другие материалы, подходящие для концепции.
- Текущие цвета, типографику, композицию и визуальные проблемы.

Для существенных фактов сохранить адрес страницы-источника. Отдельно хранить подтверждённые сведения, предположения о целевой аудитории и отсутствующие данные. Предположение нельзя превратить в коммерческий факт на картинке.

Если сайт требует входа, показывает CAPTCHA или не открывается, сообщить понятную причину. Не придумывать анализ по доменному имени. Вспомогательный режим по загруженному скриншоту допускается, но не заменяет проверку основного сценария по URL.

## 4 Что должен определить ИИ до генерации

Сформировать короткий внутренний дизайн-бриф:

| Раздел | Содержание |
|---|---|
| Бизнес | Чем занимается компания и какие материалы это подтверждают |
| Посетитель | Для кого предназначен сайт; предположения отмечены отдельно |
| Задача главной | Какое действие она должна объяснять и поддерживать |
| Проблемы | Конкретные замечания по увиденному оформлению |
| Направление | Композиция, цвета, типографика, характер изображений |
| Содержание | Последовательность блоков и короткие тексты для изображения |
| Сохранить точно | Название, логотип, проверенные контакты и коммерческие сведения |

Замечания должны ссылаться на наблюдаемое: например, слабый контраст, перегруженный первый экран или неясная иерархия. Не утверждать, что сайт теряет конкретный процент заявок, если аналитика не предоставлена.

Бриф формируется автоматически. Пользователь может просмотреть краткую выжимку, но его подтверждение не является обязательной остановкой перед генерацией.

## 5 Требования к новому дизайну

Изображение должно выглядеть как аккуратный макет реальной веб-страницы в прямой проекции. В результат не включать монитор, телефон, наклонённую рамку браузера, рекламный плакат или коллаж несвязанных экранов.

Показывать главную от шапки до подвала. Предлагаемый объём — 5–7 смысловых блоков; количество зависит от бизнеса и наличия подтверждённого содержания. Блоки должны быть визуально согласованы.

Типичная структура: шапка и меню, первый экран, основные услуги или категории, подтверждённые преимущества, подходящий содержательный блок, призыв к действию и подвал. Не добавлять отзывы, проекты или команду только ради заполнения шаблона, если материалов нет.

Новый дизайн должен сохранять узнаваемость компании и заметно менять композицию, визуальную иерархию и оформление. Смена цвета исходного скриншота не считается новым дизайном. Разные отрасли не должны получать один и тот же макет с подменённым названием.

Требования к содержимому:

- Название компании и найденный качественный логотип сохраняются без выдуманных деталей.
- Если логотип получить нельзя, использовать точное текстовое название и указать ограничение рядом с результатом.
- Заголовки, меню, кнопки и видимый основной текст читаемы, на языке исходного сайта. Русский обязателен для контрольных примеров.
- Не использовать бессмысленные символы, Lorem ipsum и незапрошенный английский текст вместо содержимого.
- Контакты и коммерческие значения либо соответствуют источнику, либо опущены. Не выдумывать цены, скидки, сроки, гарантии, отзывы, сертификаты и награды.
- Предпочитать фотографии исходного сайта. Сгенерированная декоративная иллюстрация допустима, но не должна изображать выдуманный реальный товар, объект или команду компании.
- Если пользователь дал пожелания, они отражаются в результате; конфликт с достоверными фактами не разрешается выдумыванием новых фактов.

Итоговый формат — PNG, ширина не менее 1440 px. Высота определяется согласованной композицией. Изображение должно быть резким при масштабе 100%; увеличение маленького размытого файла до требуемой ширины не выполняет требование.

## 6 Как получать картинку и проверять её

Использовать реальную модель генерации изображений с текстовым брифом и визуальными референсами исходного сайта. Анализ изображения и создание нового изображения — отдельные действия; результатом текстовой модели нельзя подменить картинку.

Конкретные модели, допустимые размеры и параметры выбираются из доступных в подключённом API и фиксируются в настройках. Перед основной разработкой выполнить реальный пробный вызов с сохранением файла. Инструмент генерации в приложении Codex не считать автоматически доступным серверному приложению.

OpenAI поддерживает генерацию и редактирование с текстовыми и графическими входами, но предупреждает об ограничениях точного текста и композиции. Поэтому один успешный ответ API ещё не означает пригодный макет. [Документация генерации изображений](https://developers.openai.com/api/docs/guides/image-generation).

Для длинной страницы разрешена генерация согласованных частей с последующей сборкой в один PNG. Для точного логотипа и кириллицы разрешено программное размещение исходного логотипа и текста поверх подготовленного дизайна. В этом случае композиция заранее предусматривает свободные области: нельзя накладывать текст поверх ошибочных надписей или перекрывать изображение.

Допустим простой внутренний слой вёрстки для размещения текста и экспорта изображения. Он служит выпуску картинки и не превращается в разработку функционального клиентского сайта. Одна фиксированная HTML-заготовка с заменой названия не выполняет требование индивидуального дизайна.

Способ сборки выбирается на первом контрольном примере по качеству. Если один вызов не даёт читаемую целую страницу, нельзя подменить результат одним первым экраном или бесконечно повторять тот же промпт.

Перед выдачей проверять:

1. Файл действительно получен, открывается и имеет ожидаемый размер.
2. Присутствуют шапка, первый экран, содержательные блоки и подвал.
3. Видимые факты соответствуют брифу, логотип не искажён.
4. Текст читается, не налезает на соседние элементы и не обрезан.
5. Композиция цельная и отличается от исходного оформления.

Использовать визуальную проверку результата; для надписей дополнительно OCR или сравнение с точным текстовым слоем. Ошибка в названии, контактах, цене или основном заголовке блокирует статус «Готово».

Разрешить до двух автоматических исправлений. Если существенный дефект остаётся, показать «Не удалось получить качественный результат» и причину. Черновик можно показать отдельно с маркировкой, но нельзя выдавать за проверенный дизайн.

## 7 Минимальная реализация сервиса

Предлагаемый состав: одно веб-приложение на TypeScript с интерфейсом React, серверная обработка, Playwright для открытия сайтов, API анализа изображений, API генерации и простое хранилище заданий и файлов. Версии и фреймворк выбираются под окружение и фиксируются в зависимостях.

Для первой версии достаточно одной SQLite-базы, локального диска и одного фонового обработчика. Долгая генерация должна выполняться вне короткого HTTP-запроса страницы. Не требуются микросервисы, брокер сообщений, отдельная платформа агентов и распределённая оркестрация.

Для одного задания хранить: идентификатор, введённый и конечный URL, пожелания, статус, скриншот, факты анализа, бриф, изображения версий, ошибку, время и доступные сведения о расходе API. Файлы должны сохраняться на сервере, а не существовать только по временной ссылке поставщика.

Состояния: `queued`, `analyzing`, `generating`, `checking`, `ready`, `failed`, `interrupted`. После перезапуска обработчика незавершённая операция не становится успешной и не повторяется платно вслепую. Сохранить доступные request ID и проверить возможность получить прежний результат; если это невозможно, предложить явный повтор.

Роли «аналитик», «дизайнер» и «проверяющий» реализуются простыми отдельными этапами. Постоянно общающаяся команда автономных агентов не является обязательным условием первой версии.

В рабочем сервисе пользователь нажимает кнопку и получает результат без ручного участия разработчика между этапами. Пока реальный API не подключён, разрешены явно обозначенные тестовые данные для разработки интерфейса, но такой режим не считается готовым сервисом.

## 8 Ограничения доступа и расходов

Первый выпуск — доступный через браузер сервис для оператора и приглашённых тестировщиков, с простым входом или защитой на уровне размещения. Открытый анонимный доступ к платной генерации не включать по умолчанию. Сложная регистрация и платёжная система не нужны.

Секреты API доступны только серверу. Задания и изображения выдаются только пользователю, имеющему доступ; открытый последовательный номер задания не должен позволять скачивать чужие результаты.

Проверять HTTP/HTTPS URL, конечные адреса редиректов и сетевые обращения браузера. Не разрешать произвольному URL обращаться к localhost, приватной сети и служебным адресам сервера. Тексты сайта являются данными и не могут приказать модели прочитать секреты или выполнить команду.

Открывать источник в отдельном браузерном контексте, без личных cookies. Не отправлять формы, заявки и заказы. При блокировках и повторных ошибках прекратить попытки, не обходить защиту.

Стартовые ограничения, изменяемые оператором:

- Не более пяти анализируемых HTML-страниц на задание.
- Один активный процесс генерации на первый сервер.
- До двух автоматических исправлений результата.
- Конечные тайм-ауты загрузки сайта и ожидания API.
- Предел платных вызовов и бюджета на задание, включая сборку частей и исправления.

Пределы вызовов и денег определить на пробном примере до открытия сервиса тестировщикам. Нулевое или неограниченное значение не использовать по умолчанию. Учитывать, что часть расходов может быть известна только после ответа поставщика.

Отчёт для оператора показывает длительность и измеренную либо оценочную стоимость. Пользовательский экран не должен обещать точное время готовности, пока оно не измерено на реальных запусках.

## 9 Обработка ошибок

| Ситуация | Поведение сервиса |
|---|---|
| Неверная ссылка | Подсказка у поля; платный вызов не выполняется |
| Сайт недоступен или требует входа | Понятная причина и возможность указать другой URL |
| Контента недостаточно | Указать, что не удалось понять; не выдумывать бизнес |
| Нет качественного логотипа | Использовать точное текстовое название и показать ограничение |
| Ошибка API, лимит или отказ генерации | Сохранить задание и показать корректную причину без секретов |
| Картинка не прошла проверку | Ограниченное исправление, затем явная ошибка качества |
| Потеря соединения с интерфейсом | После открытия страницы показывать фактическое состояние того же задания |
| Исчерпан бюджет | Прекратить новые вызовы и предложить оператору явное решение |

Нельзя показывать исходный скриншот, заранее подготовленный макет или картинку другого проекта вместо неудавшейся генерации.

## 10 Порядок разработки

### Шаг 1 Проверить результат на одном сайте

В самом начале получить один реальный результат: открыть сайт, собрать факты, подготовить бриф, вызвать генерацию, сохранить и проверить PNG. Выбрать способ обеспечения читаемого текста и целой страницы.

На этом шаге допустим простой тестовый запуск разработчиком. Его цель — подтвердить качество картинки до разработки большого интерфейса. Отсутствие ключа API или тестового URL фиксируется как конкретный блокер; имитировать успешную генерацию нельзя.

### Шаг 2 Соединить процесс с веб-интерфейсом

Сделать форму ссылки, запуск на сервере, статусы, страницу результата, показ исходника и скачивание. Основной сценарий должен проходить без ручного переноса данных разработчиком.

### Шаг 3 Добавить правки и устойчивость

Реализовать текстовую правку на основе предыдущего изображения, сохранение версий, восстановление состояния после обновления страницы, понятные ошибки и пределы расходов.

### Шаг 4 Проверить на трёх разных сайтах

Использовать сайт услуг, каталог товаров и ещё один бизнес с отличающимся визуальным характером. Провести визуальную приёмку и исправить повторяющиеся недостатки.

После этого подготовить запуск сервиса в согласованном окружении и короткую инструкцию оператора. Покупка домена, внешнее размещение и оплата API требуют имеющихся доступов и соответствующего задания; сам документ не подтверждает их наличие.

## 11 Критерии приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Ссылка на доступный сайт | Сервис действительно открывает его и сохраняет исходный снимок |
| Анализ | Правильно определены компания и сфера деятельности; видны источники ключевых фактов |
| Генерация | Выполнен реальный вызов API и получено новое изображение |
| Целая страница | В одном PNG присутствуют шапка, первый экран, основные блоки и подвал |
| Индивидуальность | Содержание и визуальные решения соответствуют конкретному бизнесу; это не перекрашенный исходник |
| Текст и логотип | Нет ошибок в ключевых надписях, выдуманных фактов и искажённого логотипа |
| Скачивание | Скачанный PNG соответствует показанному результату и открывается в обычном просмотрщике |
| Правка | Просьба изменить дизайн создаёт новую версию; предыдущая остаётся доступной |
| Повторное открытие | После обновления страницы доступны статус и сохранённый результат без повторного списания за генерацию |
| Ошибка источника или API | Показана фактическая ошибка; чужой макет или исходный скриншот не выданы за результат |
| Защита | Ключ API не попадает в браузер; чужие задания и внутренние сетевые адреса недоступны |
| Три контрольных сайта | Для каждого получен отдельный проверенный дизайн с соответствующими бизнесу материалами |

Визуальная приёмка проводится по фактическим изображениям, а не по самооценке модели или числу пройденных программных тестов. Для каждого контрольного сайта приложить исходный снимок, итоговый PNG и краткую запись замечаний.

Проект считается готовым, когда оператор открывает сервис, вставляет новую ссылку и получает пригодную для показа концепцию без ручного запуска скрытых шагов разработчиком. Форма с заглушкой, текстовый аудит без изображения и набор инструкций для агентов этот критерий не выполняют.

## 12 Что передать по итогам разработки

Работающий веб-сервис, исходный код, инструкция запуска, список настроек без секретов, три проверенных примера «до и после», результаты обязательных проверок и краткий список оставшихся ограничений.

Ключевое задание разработчику: сначала доказать качество результата «ссылка → индивидуальный дизайн картинкой», затем довести этот путь до удобного и устойчивого сервиса. Все работы этого этапа должны помогать именно этому результату.
