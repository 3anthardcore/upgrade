# Первый лицензированный Битрикс для Upgrade: исследование установки

Проверено 29 сентября 2026. Задача: `research-bitrix-install`; вход: `art-00cae2b0-b50c-4b77-a660-23d3d3771e8a`. Это записка для исполнителя установки, а не подтверждение работающего Битрикс. Секрет лицензии не читался, сервер и БД не использовались. Фактические редакция, активность ключа, версия получаемого дистрибутива и результат активации пока **UNVERIFIED**.

Рекомендуемый путь для текущего репозитория: получить подходящий коммерческий архив официальным способом вне изолированной сети назначения; установить платформу в отдельные document root и БД через временный закрытый установочный профиль; завершить мастер после создания администратора без готового решения; затем вернуть профиль демо и подключить собственный `/local`-код Upgrade. Возможность скачать архив не заменяет проверку лицензии, а выполненная установка не означает `DEMO_READY`.

## Выбор редакции и дистрибутива

Редакцию нужно взять из подтверждённых сведений владельца лицензии/официального кабинета. Нельзя выбирать «Бизнес» только потому, что сайт похож на магазин, или выводить редакцию из внешнего вида ключа. В BitrixSetup выбрать именно **«1С-Битрикс: Управление сайтом»**, русский язык для российской линейки и коммерческую версию соответствующей редакции. Документация предупреждает: при несовпадении языка, редакции и ключа возможен HTTP 403. Рекомендация «Бизнес» в примере официальной инструкции относится к демонстрационной установке, а не к любому коммерческому ключу. [Официальная установка дистрибутива](https://docs.1c-bitrix.ru/pages/get-started/install-distr.html).

Для действующей лицензии официальный способ получить коммерческий архив — войти под привязанной к ней учётной записью на сайте вендора и открыть раздел дистрибутивов. Альтернатива — штатный BitrixSetup с коммерческим ключом. [Получение дистрибутива](https://www.1c-bitrix.ru/support/faq/?ELEMENT_ID=1350306), [BitrixSetup](https://dev.1c-bitrix.ru/learning/course/index.php?COURSE_ID=32&LESSON_ID=4891&LESSON_PATH=3903.4862.4888.4891).

Если активность ключа закончилась, право на свежий коммерческий дистрибутив нельзя считать подтверждённым. FAQ указывает на версию, доступную на дату окончания активности, и получение соответствующей ссылки через владельца лицензии/вендора. Другие причины отказа — непривязанный аккаунт и неактивированный ключ. Не повторять запросы с перебором редакций и не подменять отказ установкой другой коммерческой редакции. [Официальные причины отказа загрузки](https://www.1c-bitrix.ru/support/faq/?ELEMENT_ID=1349137).

| Вариант                                 | Что подтверждено                                                                        | Применение здесь                                                                                      |
| --------------------------------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Коммерческий, `src` в форме BitrixSetup | Исходные коды; требует соответствующего коммерческого ключа                             | Предпочтительный путь после проверки редакции/активности                                              |
| Демонстрационный, `encode`              | Ознакомительная версия с защищёнными ключевыми файлами; отдельный срок использования    | Не считать активированной коммерческой установкой только из-за наличия переданного ключа              |
| Демо, затем коммерческая регистрация    | Официально предусмотрен ввод коммерческого ключа и регистрация через систему обновлений | Резервный путь, только с фиксацией фактического результата регистрации; не обход ограничений лицензии |

Основания: [официальное различие двух дистрибутивов](https://www.1c-bitrix.ru/support/faq/?ELEMENT_ID=1349137), [переход демоверсии к коммерческому использованию](https://dev.1c-bitrix.ru/learning/course/index.php?COURSE_ID=135&LESSON_ID=1947), [страница демоверсий](https://www.1c-bitrix.ru/download/cms.php). Наличие информационных Product в Upgrade не требует автоматически называть цель готовым торговым каталогом: текущий адаптер переносит редактируемый снимок через инфоблоки; Offers/цены/остатки/checkout остаются отдельной реализацией и проверкой.

### Что проверено в самом BitrixSetup

Выполнен отдельный HTTPS GET [официального `bitrixsetup.php`](https://www.1c-bitrix.ru/download/scripts/bitrixsetup.php), без PHP-исполнения и без ключа: HTTP 200, **127 760 байт**, SHA-256 **`320e2f5c6e8dd25fd591eb157133342933a735b03367e2c441c8722f2ad35121`**. Хеш совпал со входным receipt root. Это хеш загрузчика, не платформы и не будущего архива.

По прочитанному коду этой конкретной версии:

- `licence_type=src` — обозначение режима формы; имя коммерческого архива оканчивается на `_source.tar.gz`, путь формируется под `private/download/`. Имя `_src.tar.gz` не подтверждено этим кодом.
- Демо использует `download/` и суффикс `_encode.tar.gz` (есть отдельная legacy-ветка PHP5, не предназначенная для текущего окружения).
- Загрузчик записывает ключ в `/bitrix/license_key.php`. При частичной загрузке он может включать `LICENSE_KEY` в URL продолжения; запрос к серверу загрузок использует производное от ключа в query. Эти значения нельзя сохранять в открытых логах, trace, истории команд или отчётах.
- Есть механизм самообновления загрузчика. После его срабатывания первоначальный SHA уже не описывает исполняемый файл; новый файл необходимо отдельно учесть и проверить.

Это наблюдения исходного кода загрузчика, **не контракт публичного API**. Не делать из внутренних параметров BitrixSetup внешний API Upgrade. Предпочтительный для текущей изоляции путь — официальный архив, загруженный отдельным контролируемым процессом, без подключения всей CMS к Интернету. До использования web-загрузчика закрыть его loopback/аутентификацией, исключить секретные query из access/error/trace-логов и проверить, что PHP-файлы с ключом не могут выдаваться как текст. Временные загрузки и полные URL с производными ключа также считать секретными.

## Совместимое окружение

На проверенной странице продукта минимальные требования — PHP 8.2 и MySQL 8.0+. В подробной инструкции от 16.01.2026 рекомендуются PHP 8.4+, UTF-8 для платформы 24.0.0+ и MySQL с `utf8mb4` / `utf8mb4_0900_ai_ci`. Поэтому выбранный репозиторием PHP 8.3 удовлетворяет указанному минимуму; это не заменяет тест конкретного свежего дистрибутива. Не менять уже согласованный runtime молча. PostgreSQL здесь не выбирать: документация ограничивает его соответствующей лицензией Enterprise. [Требования продукта](https://www.1c-bitrix.ru/products/cms/requirements.php), [подробные серверные требования](https://dev.1c-bitrix.ru/learning/course/index.php?COURSE_ID=135&LESSON_ID=2593).

До установочного PHP проверить фактические версии и digest образов. Важны `mysqli`/MySQL, `mbstring`, OpenSSL, Hash, XML, zlib, GD/FreeType; DOM/ZIP и дополнительные расширения зависят от модулей. В текущем `infra/provisioning/Dockerfile` собираются `mysqli pdo_mysql mbstring intl zip gd soap opcache`; наличие остальных нельзя выводить только из Dockerfile — проверить `php -m` и мастер. Не переносить старую настройку `mbstring.func_overload`: в актуальных требованиях она удалена. [Серверные требования](https://dev.1c-bitrix.ru/learning/course/index.php?COURSE_ID=135&LESSON_ID=2593).

Официальный сайт допускает контейнерное окружение разработки и ссылается на `bitrix-tools/env-docker`. Это подтверждает допустимость подхода, но не безопасность или совместимость именно нашего Compose. Не запускать BitrixEnv поверх имеющегося Ubuntu-хоста с соседними сервисами: официальный сценарий BitrixEnv рассчитан на чистую ОС поддерживаемой линейки и меняет системное окружение. Здесь сохранить отдельный Compose. [Официальное окружение и Docker](https://docs.1c-bitrix.ru/pages/get-started/install-env.html).

## Изоляция до первого bootstrap: применимость репозитория

Следующие выводы получены из локальных `infra/compose/compose.yaml`, `infra/provisioning/{Dockerfile,demo.ini,prepend.php,preflight.sh}`, `infra/nginx/demo.conf`, `docs/bitrix.md`. Это review конфигурации, не испытание сервера.

| Граница                   | Уже заложено в репозитории                                                                                                                        | Что реально проверить перед установкой                                                                                                                                            |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Соседние сайты/БД         | Отдельный Compose project, отдельный volume БД, document root и приватное состояние                                                               | Разрешённые абсолютные пути, отсутствие общего production volume, отдельный пользователь БД с правами только на эту БД                                                            |
| Сеть                      | Только `isolated`, `internal: true`; web binding `127.0.0.1:PORT`                                                                                 | До PHP-bootstrap инертным процессом проверить запрет внешнего HTTPS/DNS/SMTP, host bridge, соседних контейнеров и служб; `internal: true` само по себе не является актом проверки |
| Входящий доступ           | Basic Auth, noindex, скрытые файлы запрещены                                                                                                      | Доступ без пароля отвергается; отсутствует публичный listener; нет прямой выдачи `.settings.php`, ключа и архивов                                                                 |
| Почта и фоновые действия  | `sendmail_path=/bin/false`, `mail` и process-функции отключены; prepend ставит `NO_AGENT_CHECK`, `BX_CRONTAB`, `DisableEventsCheck`; нет cron/MTA | Подтвердить действующий `auto_prepend_file` в FPM и CLI; проверить отсутствие вызовов почты/платежей/webhook; SQL event scheduler выключен                                        |
| Предустановочная загрузка | Runtime image собирается до монтирования Битрикс                                                                                                  | Архив и build dependencies получать отдельным процессом; после монтирования лицензированного/клиентского кода не открывать общий egress                                           |

**Конкретный несовместимый участок:** текущий `demo.conf` отправляет `/` и произвольные корневые пути в `/local/upgrade-route.php`; он не исполняет корневые `/index.php` и `/bitrixsetup.php` как установщик. На пустой цели route-файла ещё нет. Нужен отдельный временный installation-профиль Nginx с теми же loopback/auth/noindex ограничениями и точными разрешёнными путями установщика. Не добавлять общий обработчик всех произвольных PHP-файлов источника. После установки закрыть установочные пути и вернуть профиль Upgrade. `/bitrix/` остаётся необходимым для штатной админки.

`demo.ini` намеренно запрещает исходящие функции и устанавливает конечные лимиты: 60 секунд на PHP-запрос, upload 32 MiB, POST 36 MiB. Крупный архив следует распаковать контролируемо до PHP-bootstrap; не загружать его через ограниченную веб-форму. Мастер может показать неуспешные проверки исходящих соединений/почты либо рекомендации иных лимитов. Сохранить эти результаты как ожидаемые ограничения демо; не отключать сеть, prepend или mail-защиту ради зелёного индикатора. Обязательные локальные ошибки PHP/БД исправлять отдельно, сохраняя изоляцию. Подготовленный архив избавляет PHP-мастер от задачи загрузки дистрибутива, но возможность полностью офлайн завершить коммерческую регистрацию здесь **не проверена**. FPM worker должен иметь требуемые права только на выделенные каталоги сайта/сессий; не исправлять доступ глобальным `chmod 777` или изменением соседних сайтов.

Существующий preflight требует `bitrix/modules/main/include/prolog_before.php`, поэтому запускать его после распаковки официального архива. Он не выполняет установку и не подтверждает лицензию. Применимые проверки конфигурации при подготовленных переменных:

```bash
docker compose -f infra/compose/compose.yaml config --quiet
bash infra/provisioning/preflight.sh
```

Не выводить развёрнутую конфигурацию/секреты в общий лог. Пароли БД в Compose передаются ссылками на secret-файлы; в мастере использовать **существующие отдельные** БД и пользователя (`db` как имя сервиса в сети), не root-аккаунт MySQL и не реквизиты production.

## Минимальная установка без демонстрационного каталога

1. Зафиксировать подтверждённые продукт/редакцию, режим разработки, источник архива, размер/SHA, версии runtime и идентификатор изолированной цели. Сохранить архив вне публичной раздачи, проверить его состав и безопасные пути до распаковки. Пустота назначения проверяется явно; не распаковывать поверх установленного сайта.
2. Подготовить и проверить сеть/почту/фоновые ограничения выше; только затем разрешить первый PHP-запрос. Открыть временный установочный URL через закрытый доступ.
3. Пройти штатный мастер: соглашение, коммерческий ключ, **«Установка для разработки»**, проверка системы, реквизиты отдельной существующей БД, установка платформы, создание администратора. Не подставлять придуманные сведения владельца и контакты. Порядок шагов может отличаться; официально мастер создаёт системные таблицы и файлы. [Мастер дистрибутива](https://docs.1c-bitrix.ru/pages/get-started/install-distr.html).
4. После создания администратора **не выбирать интернет-магазин, мебельную компанию, банк или Marketplace-решение**. Официальная чистая установка позволяет закрыть мастер решения и удалить установочный `index.php` из корня. Для нашего воспроизводимого процесса сначала сохранить хеш/копию этого конкретного файла вне web-root, затем убрать его из исполнения. Это завершение официальной установки, не редактирование ядра или удаление произвольных файлов поставщика. [Чистая установка](https://docs.1c-bitrix.ru/pages/get-started/install-solution.html).
5. Подтвердить вход в штатную админку; сохранить версии платформы и нужных модулей, состояние лицензии/режима разработки без ключа, исходные количества сущностей. Системные агенты/типы/служебные записи могут существовать и в чистой платформе: не считать их клиентским контентом, не удалять вручную. Демокаталог с чужими товарами/ценами не импортировать.
6. Закрыть/удалить только учтённые временные установщики и архивы; проверить ответ на их прежние URL. BitrixSetup по документации удаляется после распаковки, но это нужно проверить фактически. Переключить на собственный профиль Upgrade. Создать проверяемый backup чистой цели перед модулем/импортом; затем выполнять отдельные validate/dry-run/import/reconcile/HTTP/admin/restore испытания. [Жизненный цикл BitrixSetup](https://dev.1c-bitrix.ru/learning/course/index.php?COURSE_ID=32&LESSON_ID=4891&LESSON_PATH=3903.4862.4888.4891).

Документированный Short install существует, однако он пропускает части мастера через подготовленную `.settings.php`. Для первого пилота предпочтителен наблюдаемый обычный мастер: Short install нельзя трактовать как замену проверки соглашения, лицензии, локальных параметров и изоляции. [Описание Short install](https://docs.1c-bitrix.ru/pages/get-started/install-distr.html).

## Соглашение, активация и границы демо

Принятие EULA — отдельный фиксируемый шаг штатного мастера; это не просто технический checkbox с автоматически известным ответом. На момент исследования официальный PDF имеет редакцию 27.05.2025 и связывает начало использования с согласием на условия. Исполнитель должен действовать в рамках уже полученного от владельца поручения; эта записка сама не предоставляет дополнительных полномочий. Если соответствующее поручение и сведения уже сохранены root, повторно спрашивать их не требуется. [Текущий официальный EULA](https://www.1c-bitrix.ru/download/law/eula_bus.pdf).

Переданный ключ может быть уже активирован. Тогда не нужно заново придумывать владельца или регистрировать ключ на исполнителя: официальная инструкция предусматривает регистрацию установленного продукта в системе обновлений. При первой активации понадобятся реальные сведения владельца, контактного лица, адреса сайтов и тестового адреса, привязанный аккаунт; это отсутствующие существенные данные, если они не предоставлены ранее. Активация/регистрация обращается к вендору и меняет лицензионное состояние; без фактического ответа её результат **NOT_RUN/UNVERIFIED**, а не PASS. [Регистрация коммерческого продукта](https://dev.1c-bitrix.ru/learning/course/index.php?COURSE_ID=135&LESSON_ID=1945), [активация ключа](https://www.1c-bitrix.ru/support/faq/?ELEMENT_ID=1350180).

Для разработки официальный режим включается при установке либо в настройках Главного модуля / Система обновлений. Документация требует не использовать его как боевой сайт и рекомендует отключать автоматическую проверку обновлений на дополнительных установках. Не переключать режим для обхода учёта установок. Открытый публичный сайт и закрытое демо — разные лицензионные состояния; пароль/noindex не являются подтверждением всех прав на публикацию. [Установка для разработки](https://dev.1c-bitrix.ru/learning/course/index.php?COURSE_ID=135&LESSON_ID=8471), [официальные ограничения копий](https://www.1c-bitrix.ru/support/faq/?ELEMENT_ID=1355248).

Если серверная регистрация действительно требует выхода в сеть, сначала определить точные официальные адреса по документации/контролируемому запросу и отдельную ограниченную процедуру. Не обещать офлайн-активацию и не разрешать произвольный egress контейнеру с кодом/данными клиента. Отказ лицензии либо недостающие сведения блокируют соответствующую регистрацию, но не отменяют выполненную независимую подготовку окружения.
