## Обнаруженная граница исходной реализации

До исправления просмотренный код принимал HTML со статусом 200 на `/robots.txt` в `parseRobots`. Отсутствие распознанных директив давало пустые правила и фактический allow-all. Для страницы HTML 200 становился `FETCHED`, после чего запускались `inspectHtml` и, в browser-режиме, рендеринг. Это могло принять текст проверки посетителя за контент или начать исполнение challenge-скриптов. Оценка получена чтением кода, а не новым обращением к защищённому источнику.

Необходимые свойства исправления:

- Известная страница проверки классифицируется до извлечения контента и запуска браузера, независимо от успешного HTTP-кода.
- HTML вместо robots не означает разрешение обхода. Сохраняются ответ, HTTP/MIME, хеш и конкретная причина остановки.
- Начальный URL и уже найденные адреса остаются в исходном реестре как неразрешённый объём; их нельзя превращать в успешные страницы или исключать ради процента полноты.
- Состояние приостановки и расход запросов переживают restart. Обычный повтор `run/crawl` не делает бесконечных попыток. Разрешённое возобновление требует явного подтверждения изменённых условий и конечного лимита.
- Повторная HTTP-загрузка на границе browser transport также проверяется: исходный preflight мог вернуть обычный HTML, а browser GET — challenge. Такой ответ нельзя отдавать Chromium для исполнения.
- Старое сохранённое состояние с ошибочным `COMPLETE/FETCHED` challenge не должно проходить reuse/extraction по прежней классификации. Нужна повторная локальная проверка снимка либо явный отказ от несовместимого состояния, без нового запроса к источнику.
- Challenge-ссылки, картинки, формы, cookies и встроенные указания не создают задачи переноса и не расширяют полномочия агентов. Возможны консервативные false positives и неизвестные виды защит; их нужно отражать как границы детектора.

Первая frozen-реализация выполняет эти свойства для известного title KillBot и явного заголовка `cf-mitigated: challenge`. Независимо запущены 26 тестов краулера/извлечения, включая реальный локальный Chromium, смену обычного HTTP на challenge при browser GET, сохранение SHA и source URL, запрет обычного повторного запроса, одноразовый acknowledgement, неизменность расходов, перенос каталога снимков и offline-отказ от legacy challenge. Сохранённый локальный `home.html` независимо передан детектору как байты: классификация `KillBot / ACCESS_CHALLENGE`, SHA совпал.

В дополнительном локальном fixture reviewer воспроизвёл ещё один край: `/robots.txt` с HTTP 200, `Content-Type: text/plain` и телом `<div><h1>Sign in</h1></div>` не распознавался как HTML, давал `robots_done=true` и `COMPLETE`; выполнялись запросы `/robots.txt`, `/sitemap.xml`, `/`. Замечание исправлено автором после review: markup fragment распознаётся независимо от конкретного корневого тега, обычный robots-комментарий с примером HTML остаётся текстом. Независимый повтор 27/27 тестов PASS включает настоящий локальный HTTP fixture: `ROBOTS_HTML`, `PAUSED`, evidence принадлежит `/robots.txt`, homepage body отсутствует, только один GET, обычный restart не повторяет доступ. Реальный пилот для воспроизведения не запрашивался.

Детектор намеренно узкий: он не доказывает распознавание любой защиты. Если известный title возник только после JavaScript в ранее нераспознанной странице, код уже выполнялся в ограниченном браузере; тест подтверждает остановку до извлечения модели и обхода обнаруженных challenge-ссылок после детекции. Утверждать запрет исполнения всех динамических challenge-скриптов по этому тесту нельзя. Для известного HTTP challenge ответ блокируется до `route.fulfill` и его скрипты не исполняются.

Первый frozen reporter прошёл 9 независимых запусков persisted Store → JSON/HTML/Markdown: исходный URL, известный знаменатель, неизвестный размер сайта, active access block, source-bound legacy guard и отсутствие влияния устаревшего guard на новый артефакт отражаются правильно. Прямой `report` по legacy `COMPLETE` без `access.version=1` и без ранее записанного `source-access-error.json` ошибочно выдавал `source.gate=COMPLETE` и следующий шаг «Настроить изолированный Битрикс». Это исправлено после review: report сам консервативно показывает `ACCESS_REVALIDATION_REQUIRED`, effective state `PAUSED`, сохраняя `recorded_state=COMPLETE` и `recorded_fetched`, но `fetched=0`. Причина помечена `report-compatibility-check` и связана с исходным artifact ID; сам Store/исходный снимок не мутируется и сеть не вызывается. Независимый повтор 10/10 тестов PASS включает три legacy-варианта: отсутствие access, отсутствие version и version=0.

Первая frozen-версия Pipeline/CLI независимо прошла `npm run check` и 2 CLI E2E (отдельные процессы; правильный ack, no-ack, legacy challenge/legacy robots перед extract/build). Дополнительный собственный CLI fixture выявил потерю операторского ограничения: первый `crawl --max-requests 1` остановился с code 3, `PAUSED`, requests=1; после `resume` и ack без повторного max-флага получилось code 0, `COMPLETE`, requests=4. Причина: Pipeline сохранял только mode/fixtureOrigins и подставлял default 65000 при следующем процессе. Счётчик не обнулялся, но разрешённый предел молча увеличивался. По §8 ТЗ увеличение требует отдельного зарегистрированного решения. Дополнительно статически установлено, что `build` проверял access marker, но не `crawl.state===COMPLETE`; это могло допустить старую модель при современном PAUSED без активного challenge.

Оба замечания корень исправил. Effective limits и rate сохраняются до запроса; отсутствие флага сохраняет прежний предел, явное увеличение отклоняется code 2 до сети. Process signal и одноразовый access acknowledgement не сохраняются как повторно применимая конфигурация. Старый snapshot без записанных исходных numeric limits приостанавливается с code 3 до сети: восстановить неизвестный операторский предел из default нельзя. Для такого legacy случая требуется сохранить evidence и явно спланировать новый проект/snapshot; отдельный протокол увеличения бюджета в этот исправленный scope не входит. Современный `PAUSED` блокируется до build и до чтения старой модели. Финальный независимый запуск 3/3 CLI E2E PASS подтвердил предел 1 после restart, отклонение увеличения, legacy unknown-limit gate, отсутствие release и legacy guards перед extract/build. Точный собственный первоначальный repro с challenge и ack также повторён: оба вызова code 3, после ack `PAUSED`, requests=1, единственный GET `/robots.txt`, `started_at` неизменён.

## Легитимные условия продолжения пилота

Для автоматического серверного обхода корень уже запросил у пользователя один из вариантов; reviewer не дублирует запрос. Штатное ручное исследование во встроенном браузере теперь отдельно разрешено пользователем и доступно по наблюдению корня:

1. Владелец/администратор источника разрешает чтение с рабочего IP `148.135.208.53` и фиксированного UA UpgradeResearch в согласованном объёме. После подтверждения выполнить ограниченную проверку обычных `/robots.txt` и стартовой страницы, затем продолжить сохранённый обход с лимитами. Наличие whitelist не заменяет согласование scope и правил доступа.
2. Владелец предоставляет штатную выгрузку исходной платформы и файлов. Для проверяемого переноса нужны исходный реестр URL/редиректов, устойчивые ID и связи, тексты/SEO, локальные медиа и, если магазин включён в scope, наблюдаемые цены с валютой/единицей/условиями, наличие и реальные варианты. Платформа пока не установлена, поэтому конкретный формат экспорта CMS нельзя объявлять известным.

Не требуется передавать в репозиторий пароли, личные cookies или production-ключи. Решение CAPTCHA автоматизацией, подмена браузера ради защиты, вращение IP и подбор проверочных токенов не являются частью работ. Обычное разрешённое пользователем открытие публичного сайта в интерактивном браузере учитывается отдельно от исполнения недоверенного snapshot краулером. По сообщению корня лицензионный ключ целевого Битрикс получен и сохранён вне Git; reviewer его не запрашивал и не читал. Само наличие ключа не подтверждает установку/редакцию, изоляцию назначения и реальные интеграционные проверки.
