# Isolated Bitrix runtime for teplypol-market

Preparation is separate from source discovery; the server access block remains recorded. User confirmed Business edition. Its official commercial archive was downloaded without exposing the key, 398347933 bytes, SHA-256 `6dbc63006909d1f0b8661336476b97a8cc10a9a637f819ce67b1f9b5d598ff250`. Download proves receipt of an archive, not activation or a working CMS.

The dedicated target is `/opt/upgrade/targets/teplypol-market`. Before any CMS mount: create a labeled internal bridge `upgrade-teplypol-market-isolated`, interface `br-upgrade-tp`, subnet `172.30.50.0/24` after checking overlaps. This corrects the shorter network name in the initial intent; the project binding remains `teplypol-market`. `isolate-network.sh` adds rules scoped to this bridge: block new connections to host services and cross-network forwarding; permit replies to legitimate host connections. Existing host sites and their rules are preserved. Secrets are private files, never compose values or CLI arguments.

The runtime uses root-owned configuration and only its own document root, state and DB volume, with Basic Auth/noindex. Docker Engine 29.1.3 does not publish a port from a container attached only to an internal network. The actual ingress is host Nginx at `127.0.0.1:8090` and the authenticated HTTPS vhost `upgrade.help-ai-ru.ru`, proxying without URI replacement to the pinned internal Nginx address `172.30.50.4:8080`. There is no additional container network. PHP is built from pinned PHP 8.3; MySQL 8.0 and Nginx 1.28 images have recorded digests. No automatic restart is configured: after daemon/host restart the guard must be checked/applied and probes repeated before starting CMS. Firewall persistence and unattended restart are not yet implemented.

`probe-isolation.php` uses only fixed operator-selected canaries: own DB must connect; host SSH, host HTTPS, a disposable listener on a separate test bridge and public HTTPS must fail. Production databases are not probed. Reachability of negative canaries must be confirmed outside the isolated network first. It checks external DNS resolution, effective PHP prepend and every disabled mail/process function, recording socket error and elapsed time. Failed DNS resolution alone does not prove absence of DNS packets; resolver configuration/egress require separate evidence. No source files, license, customer data or CMS scripts are mounted during probes.

The guard checks exact rule order inside its own chains and a unique first jump in INPUT/DOCKER-USER. It refuses foreign contents in owned chains. This first-pilot profile does not coordinate multiple simultaneous guard chains: a later guard can require rechecking ordering before another demo starts. It must not be advertised as complete multi-project firewall orchestration.
