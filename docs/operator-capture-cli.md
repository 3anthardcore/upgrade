# Приём operator capture через CLI

Задача `integrate-operator-capture-cli`, вход `art-72bbc2d6-a387-4712-83da-b088cdd5a933`. Это локальный приём проверяемых наблюдений; сбор браузером, извлечение модели и импорт в Битрикс выполняются отдельно.

```text
node packages/cli/index.ts operator-capture ingest --project PROJECT --data-dir PRIVATE_DATA --directory CAPTURE_DIRECTORY --manifest-sha256 TRUSTED_SHA256
```

Проект и run должны уже существовать (`init`, `plan`). Необязательный `--manifest` задаёт относительный путь вместо `operator-capture.json`. Pin должен относиться к выбранным неизменённым байтам манифеста, а не браться из недоверенного поля пакета. Формат описан в `docs/operator-capture.md`; замечание того документа о неподключённом CLI относится к первоначальному автономному валидатору, эта команда добавляет хранение ядром.

Приём использует maintenance dispatcher lease, поэтому допустим для PAUSED run и не снимает его блокировку. Читает все исходные `raw_url`, `raw_urls`, `crawl_key` из последнего проверенного crawl artifact и передаёт их валидатору как прежний знаменатель. Исходный crawl artifact, его сетевые статусы, `active_block_id`, readiness, задачи и целевая БД не изменяются. Объединённый inventory сохраняется отдельно: полное число страниц источника остаётся UNKNOWN, доступ — NOT_VERIFIED, готовность — NOT_EVALUATED.

После автономной проверки каждый файл повторно читается через ограниченный дескриптор без symlink/hardlink, сверяется с pin по размеру и SHA-256; в `Store.publishArtifact` передаётся тот же Buffer. Копирования изменяемого пути после проверки нет. Сохраняются исходные байты манифеста и каждого материала, включая форматирование JSON; DOM/скрипты не исполняются. Имена артефактов непрозрачны, привязка исходного относительного пути к artifact ID записана в receipt.

`operator_capture` хранит PENDING/COMMITTED по capture ID и manifest SHA. Иной SHA при том же ID отклоняется. Детерминированные типы артефактов позволяют сверить уже зарегистрированную запись перед повтором после неизвестного исхода публикации. COMMITTED появляется только после всех файлов и проверенного результата. Повтор возвращает прежние artifact IDs (`replayed: true`) и проверяет их целостность. При прерывании файлы, успевшие зарегистрироваться, остаются неизменяемыми; повтор с тем же исправным пакетом завершает PENDING. Привязка к исходному crawl artifact фиксируется при первом приёме: после появления нового crawl snapshot повтор остаётся воспроизведением старого capture, не изменяет новый snapshot и не переписывает старый результат. Для наблюдений относительно нового исходного scope нужен новый capture ID. В результате `files` сохраняет исходные file references с размерами; `artifact_files` содержит отображение в Store. Осиротевшие файлы, оставленные низкоуровневым сбоем до регистрации Store artifact, автоматически не удаляются и не считаются принятыми материалами.

Команда не выполняет сеть, crawl, подтверждение доступа, автоматическое extract/build, запуск source PHP/JS, запись в целевой Битрикс или продвижение готовности. Подлинность браузерного происхождения и истинность исходных фактов остаются предметом независимой проверки. Неизвестные защиты, полнота DOM, HTTP-статус и сценарии не выводятся из наличия снимка. Для replay используется исходный portable capture; receipt и принятые файлы живут в проектном Store после закрытия чата/процесса.

Проверка: `npm run check`; `node --disable-warning=ExperimentalWarning --test tests/e2e/operator-capture.test.ts`. Тестовые проекты находятся только в проверенном временном каталоге, production/пилотный Store не используются. Проверяются настоящий CLI subprocess/restart, перенос capture directory, точные байты, прежний URL-знаменатель и PAUSED block, конфликт идентичности, подмена между validation/publication и восстановление после неизвестного результата записи.
