# Исправление владения после восстановления Upgrade

Дата: 29.09.2026. Задача: `fix-restored-lease-20260929`. Вход: принятый `restore-lease-repro.json`, воспроизводящий сценарий `var/evidence/restore-lease-repro.ts`.

## Причина и исправление

`backupProject` вызывается из `Pipeline.locked(..., {maintenance:true})`. SQLite backup корректно сохраняет состояние в момент копирования, включая действующий `dispatcher_owner` и ещё не истёкший TTL. Ранее восстановление переносило этот lock на новую независимую копию. `resumeRun()` его не очищает, поэтому немедленная попытка работы завершалась ошибкой `Dispatcher already owned`.

После проверки файлов backup и неизменяемых артефактов `restoreProject` теперь выполняет одну транзакцию **только в восстановленной SQLite**:

- У всех runs сбрасываются непереносимые `dispatcher_owner`/`dispatcher_until`. Run ID, фаза, лимиты, начало бюджета и история сохраняются.
- Задачи со статусом `RUNNING` становятся `BLOCKED`: предыдущий fencing token увеличивается, активные lease-owner/lease-until удаляются. Номер попытки, её время, входы, лимиты и прочие данные сохраняются. Исходный worker может продолжать работу на исходном хосте; его старый token недействителен в восстановленной копии.
- Резерв такой попытки переносится из `budget.reserved` в `budget.unknown`. Сумма `spent + reserved + unknown` сохраняется; неизвестный расход не становится нулевым. Несогласованная сумма резерва останавливает восстановление с ошибкой, а не исправляется округлением/обнулением.
- Активный run с такими задачами становится `BLOCKED`. Даже после явного `resumeRun()` задачи остаются неclaimable: повтор неизвестного побочного эффекта не запускается автоматически.
- `VALIDATING`, `ACCEPTED` и другие незапущенные/завершённые задачи не изменяются. В частности, автор уже переданного результата сохраняется, чтобы автор не мог принять собственный результат после restore.
- Добавляются события `task.restore_reconciliation_required`, `dispatcher.restore_detached`, `restore.completed`; исходная история не переписывается. `events.jsonl` восстановленной копии обновляется из её SQLite. Ответ restore содержит IDs снятого dispatcher ownership и задач, требующих сверки.

Ни исходный проект, ни исходный архив не изменяются. Владение внешней целевой БД и настоящие процессы не переносятся и не отменяются данным исправлением.

Новая регрессия создаёт настоящий backup внутри `Pipeline.locked`, восстанавливает и начинает работу немедленно, **пока исходный dispatcher всё ещё удерживает свой неизменённый lock**. Дополнительно сверяются неизменность исходных событий/бюджета/lease, прежний хеш файла SQLite в backup и сохранение префикса истории в новой копии.

Вторая регрессия покрывает действующего worker, ранее переданный результат, принятую задачу и готовую незапущенную задачу. Поздние heartbeat/publish отклоняются, неизвестная задача неclaimable после resume, автор результата по-прежнему не может выполнить self-review. Исходный worker сохраняет действующий token. Повторный backup/restore уже заблокированной копии не удваивает `unknown` и не меняет её fencing повторно.

## Границы

Это исправление восстановления состояния Upgrade, не подтверждение восстановления Битрикс или сверки внешней записи. `BLOCKED` с причиной `SOURCE_WORKER_OUTCOME_UNKNOWN` требует независимой сверки результата/побочного эффекта и расхода перед новым разрешённым выполнением. Новый автоматический механизм reconciliation, новая команда unblocking и изменение Codex job-артефактов не добавлены; сохранённые job-файлы являются свидетельствами предыдущего запуска, а не доказательством живого процесса новой копии.

Область изменений: `packages/core/backup.ts`, `tests/integration/backup.test.ts`, данный отчёт. Приёмку проводит независимый reviewer; автор исправления не принимает свою задачу.
