# Независимая проверка dispatcher heartbeat — 2026-09-30

**Вердикт: ACCEPT для перечисленных исходников и локальных поведенческих границ.** Нативный повтор ingest v7 на сервере этим review не выполнялся и остаётся отдельной проверкой root. Состояние пилота, сервер, целевая БД и код реализации не изменялись.

Сохранённая задача: `dispatcher-review-20260930`, исполнитель `commerce-model`, fence 1. Начальные входы: `art-2193b768-64d6-4b85-b8f3-345e1d7394bc`, `art-67afa247-afed-4382-95e4-9ca6f2a1c9eb`; начальный input hash `b64db14ffb120c4a6dfe6be1f7e7e7472c684ea254ca6d38a205c2f0e7405ab4`. Во время проверки root передал исправленную финальную версию `pipeline.ts`; ниже закреплена именно она. Store input revision сохраняет root.

## Исходная ошибка и проверяемое изменение

По входному свидетельству root нативный ingest оставил PENDING и завершился `Dispatcher ownership lost` после примерно 1200 файлов: синхронная публикация не давала исполняться таймеру и заново перечисляла все артефакты для каждого файла. Код теперь один раз индексирует deterministic artifact types, сохраняет индекс после публикации и уступает event loop между ограниченными файлами. COMMITTED replay и чтение принятых immutable bytes перед моделью также уступают event loop. Перед следующей операцией сохраняется проверка владельца и срока lease.

`renewDispatcher` выполняет проверку и продление в транзакции, отвергает уже истёкший срок и чужого владельца. Завершающая проверка `Pipeline.locked` предотвращает успешный возврат после утраты lease даже до первого срабатывания таймера. Начальная проверка ACTIVE не ослаблена; явный maintenance по существующему контракту разрешает работу с частичным источником.

История исправления: первоначальный SHA `59ecd7bfb4c01f197fa617a73c19c9d8ec7ff275e9ece0bbe2aa23e7b7f84f5c` вызывал финальный `assertOwnership(false)`, поэтому отвергал намеренный PAUSED/BLOCKED и терял обычный CLI JSON-результат. Это независимо видно из кода и существующего CLI контракта; root воспроизвёл E2E failure и исправил до deploy. Финальная проверка `assertOwnership(true)` проверяет owner/lease, сохраняя штатный конечный результат. Она не является повторной проверкой общего wall-time бюджета; начальная и стадийные проверки остаются на прежних местах.

Авторские проверки повторены на настоящих временных файлах и SQLite: реальный timer callback продлевает lease при синхронной работе; takeover между файлами останавливает публикацию; неизвестный исход публикации и результата сверяется после перезапуска без дублей и без смены исходного source binding. Сжатие lease в stress fixture начинается только на публикации: 1500 ms против более 1800 ms работы, а не на потенциально медленном первоначальном валидировании. Это поведенческий stress test, не результат измерения производительности полного пилота.

Девять независимых проверок добавлены только в разрешённую evidence-область:

- PAUSED и BLOCKED возвращают своё намеренное содержимое и освобождают собственный lease.
- Истёкший lease непосредственно перед возвратом отклоняется без ожидания timer callback в обычном и maintenance режимах.
- Перехват через отдельное SQLite-соединение отклоняет результат в обоих режимах; `finally` не освобождает lease нового владельца.
- Запуск обычной стадии на уже PAUSED run по-прежнему запрещён до вызова callback.
- Immutable preflight модели реально выполняет macrotask до чтения первого declared payload, а не только после всего цикла.
- Takeover в этой macrotask останавливает модель до следующего payload и до публикации model intent; принятый capture остаётся COMMITTED.

Тестовые проекты создавались только в специально проверяемом временном каталоге и удалялись после закрытия обоих соединений. Полный unit/integration suite не дублировался; его результаты root не подменяют приведённые независимые проверки.

## Границы

Yield происходит между файлами; один синхронный read/hash/fsync/SQLite вызов не становится прерываемым. Если отдельная операция превысит lease, последующая проверка должна отказать, а уже совершённая запись остаётся неизвестным исходом для детерминированной сверки. Проверки подтверждают отказ и restart/reconcile, но не гарантируют время обработки на произвольно медленном диске. Нет повышения TTL, возрождения истёкшего lease, автоматического снятия source block либо продвижения DEMO_READY.

Следующий шаг root: закрепить окончательные pins в Store, развернуть проверенную ревизию и выполнить нативный resume сохранённого PENDING capture с фактическим количеством артефактов и отдельным отчётом.
