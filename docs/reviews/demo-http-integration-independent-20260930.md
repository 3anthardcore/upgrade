## Блокирующие замечания

### W1 — P1: штатный POST формы не проходит строгую проверку Origin

`demoweb.php:14` и `interactive-demo.conf:38` задают `Referrer-Policy: no-referrer`. Автор DemoView сообщил фактический результат локального Chromium с отключённым JavaScript и настоящими PHP + Engine + Web + View: при отправке собственной формы `/__upgrade/action` запрос имел `method: POST`, `Origin: null`, `Content-Type: application/x-www-form-urlencoded`. Ответ — 403 и «Форма недействительна». Эти заголовки независимо подтверждены чтением замороженных исходников. Браузерный запуск выполнен другим исполнителем; данный рецензент не выдаёт его за собственный повтор или проверку сервера.

Команда воспроизведения автора: `node --test --test-name-pattern='real PHP \+' tests/integration/demo-view.test.ts` с `UPGRADE_PHP_BIN` и `UPGRADE_PHP_EXT_DIR`. Это был частичный, не успешный полный браузерный сценарий. Его обнаружение изменяет предварительную оценку Web после PHP-тестов на REJECT.

Исправление: согласовать `Referrer-Policy: same-origin` в обоих слоях и повторить настоящую отправку формы без JavaScript. Строгую проверку Origin не ослаблять; `null`, чужой origin и неверная схема должны по-прежнему отклоняться. Нужен регрессионный браузерный тест, поскольку вручную заданный Origin в PHP subprocess этого дефекта не обнаруживает.

### R1 — P2: квота runtime не учитывает файлы незавершённой записи

`demoruntime.php:18–23` считает только `*.json`. DemoEngine намеренно сохраняет `.json.pending-*` при неизвестном результате записи. Независимый тест с настоящим PHP и неизменённым `DemoRuntime::handle` создал во временном private-каталоге остаточный файл `aaaaaaaa…aaaaaaaa.json.pending-abrupt` размером **146 800 640 байт (140 MiB)**. Это уже больше заявленного общего предела 128 MiB. Канонических JSON не было. Запрос GET `/__upgrade/cart` вернул **200**, `new_cookie: true` и создал новые JSON и lock; остаточный файл сохранился.

Следовательно, проверка не обеспечивает заявленный общий предел. Это локальный воспроизводимый сценарий, а не утверждение о заполнении серверного `/var/lib/upgrade`.

Исправление: под общим admission flock учитывать все допустимые regular-файлы состояния, включая pending и lock, а также их количество. Проверять типы, симлинки и размер без автоматического удаления или продвижения pending. Сохранять блокировку на весь участок допуска и операции. Регрессия должна проверять именно остаточный файл, отказ до создания новой сессии и сохранность неизвестного результата.

### R2 — P2: private-root допускается внутри document-root

`demoruntime.php:30` отвергает только равенство `realpath(stateRoot) === realpath(DOCUMENT_ROOT)`. Независимый PHP-сценарий создал `DOCUMENT_ROOT = temp/public`, `stateRoot = temp/public/private`; указателя `demo-active.json` ещё не было. Вызов `DemoRuntime::snapshot('review', stateRoot)` вернул **null**, не `DEMO_PRIVATE_ROOT_REQUIRED`.

Следовательно, универсальный контракт разрешает размещение приватного указателя/снимка под webroot. Текущий фиксированный серверный путь `/var/lib/upgrade` находится вне webroot; его компрометация этим тестом не утверждается.

Исправление: до поиска указателя отвергать и равенство, и канонического потомка document-root с корректной границей разделителя; добавить проверку дочернего пути и одноимённого соседнего каталога.

### R3 — P2: наблюдаемый атрибут `__proto__` теряется в проекции

В `demo.ts:36` наблюдаемые имена присваиваются в обычный объект `{}` через `attributes[name]`. Независимый Node-сценарий передал JSON-объект с собственными наблюдаемыми полями `__proto__` и `Цвет` и действительными связями entity/source URL/route. Результат:

```json
{"input_attribute_keys":["__proto__","Цвет"],"output_attribute_keys":["Цвет"],"unexpected_array_prototype":true,"serialized":"{\"Цвет\":[\"белый\"]}"}
```

Изменён прототип только результирующего объекта; глобальное загрязнение прототипа или исполнение кода этим сценарием не доказано. Однако одно фактическое поле молча отсутствует в JSON и фильтрах.

Исправление: словарь без прототипа или создание собственных data-properties; регрессия для зарезервированных имён с сохранением поля при сериализации. Фактические исходные значения не переписывать.

## Подтверждённые границы реализации

По исходникам и PHP-контрактам Web сохраняет строгие Origin/CSRF и snapshot-проверки, ограничивает тело и число параметров, отклоняет дубли decoded-ключей и неизвестные поля, не принимает клиентские цены/персональные данные. Неизвестная или некорректная сессия в POST не создаётся; новые сессии получают серверный случайный идентификатор. PRG ведёт только на собственный receipt с operation SHA; история receipt привязана к сессии и может показывать сохранённый прежний snapshot, тогда как текущая корзина использует текущий снимок. Ошибки редактируются по allowlist и не раскрывают неизвестные сообщения исключений.

В runtime путь release берётся из приватного указателя, не из запроса; проверяются project/target, SHA, ограниченная форма относительного пути, отсутствие симлинка, размер и фактический хеш снимка. За исключением R2 это подтверждено чтением кода; полный положительный Linux-путь ещё требует выполнения.

Router проверяет собственный prepend/отключённые функции до CMS bootstrap, связывает project env с собственным модулем, разрешает исходные маршруты через сохранённые exact request targets. Параметр входящего cookie изолирован от CMS, дубли собственной cookie отклоняются. Названия обычных страниц берутся из импортированных полей; статусы исходных маршрутов сохраняются, собственные страницы используют фиксированные заголовки. Итоговая разметка H1 и визуальная готовность нового шаблона находятся вне этой приёмки.

Импортёр использует конечный claim 3600 с; Gateway допускает только 30–3600 с, проверяет owner/token/срок и единственного писателя. В этой задаче проверены исходники, а не новый фактический native import.

### G1 — P1: новый leading guard prefix не доказывает владение предыдущими цепочками

В `isolate-network.sh` последняя Python-вставка принимает предыдущий jump в leading prefix только по форме имени `UPG_F_[0-9a-f]{10}` (для INPUT также по форме bridge). Marker проекта, соответствие SHA project имени цепочки и реальные правила этой предыдущей цепочки не проверяются. Поэтому правило, которое только похоже на управляемое, может обработать пакет раньше собственного guard.

Независимый offline-свидетель выполнил **саму последнюю Python-вставку без изменения её кода**, заменив только `subprocess.check_output` на ограниченные заранее заданные ответы чтения и запретив `check_call`. Реальные iptables не вызывались. Данные:

```text
DOCKER-USER:
  -A DOCKER-USER -j UPG_F_0000000000
  -A DOCKER-USER -j UPG_F_1111111111
UPG_F_0000000000:
  -A UPG_F_0000000000 -j ACCEPT
```

Текущая собственная цепочка — `UPG_F_1111111111`; её scoped-правила могут быть корректны. Последний блок в режиме `check` всё равно **ACCEPTED**. Фактический список запрошенных цепочек: `["INPUT", "INPUT", "DOCKER-USER", "DOCKER-USER"]`; предыдущую `UPG_F_0000000000` он вообще не читал. В таком порядке предыдущий безусловный ACCEPT завершает обработку до собственного guard. Предыдущие вставки скрипта проверяют только текущие собственные цепочки, поэтому этот пропуск ими не закрывается.

**Guard v2 отклонён.** Это доказательство поведения кода на модели iptables, не живой тест firewall и не утверждение, что такая цепочка присутствует на сервере.

Узкое исправление для следующей версии: каждую предыдущую цепочку в разрешённом префиксе связать с собственным root-only marker через project SHA, network и bridge; проверить канонический marker без симлинков и точный допустимый набор/порядок реальных правил этой цепочки. Не принимать ACCEPT/RETURN/произвольные jumps в forward guard. Для INPUT допускается только проверенный другой bridge и известная собственная последовательность established/reject. Чужое или неподтверждённое правило должно оборвать допустимый prefix, после чего собственный guard необходимо безопасно переместить перед ним либо отказать в check. Сохранять чужие правила и сначала добавлять защитный jump, затем удалять только точные собственные дубли.
