## Bounded next software milestone: executable native handoff and readiness

The first integration should support the existing **single-origin public-demo content snapshot profile** and a configured target. It must not pretend that this also implements native catalog SKU or production. Reuse accepted code rather than making a new shell-based transport.

1. **Unprivileged coordinator:** `upgrade run/import/verify` executes as OS user `upgrade`, owns the project Store, selects the exact COMMITTED ordinary/operator build and validates its current model/scope/code/package pins. It may consume an explicitly accepted partial operator scope while leaving source discovery PAUSED; it must not fabricate a COMPLETE crawl. A durable stage intent identifies project, run, build, model, scope, package SHA, target profile reference, action, dependency receipts and deterministic request ID. Neither private profile contents nor credentials enter the Store.
2. **Explicit privileged operator step:** the coordinator emits a bounded immutable handoff request and its SHA. A real CLI executor, invoked by the already authorized root operator with that SHA and its **root-private configured profile**, copies/validates the exact package into private staging and calls the existing native driver. The target profile owns the canonical target/journal mapping; the unprivileged request cannot choose a fresh journal, executable, shell command, Docker container or unrelated filesystem path. `upgrade` receives no Docker-group membership, general sudo shell, root credentials or public privileged service. The executor never opens the project Store. This root step is an executable, reproducible part of the runbook, not a decorative plan printer.
3. **One target writer and durable unknown outcomes:** preserve the existing root-owned authoritative native journal and Gateway lock/claim/fence. Repeated or interrupted handoffs first inspect/reconcile that same journal; no new journal to bypass UNKNOWN, and no blind apply/activation retry. Record own-code/config/snapshot activation separately, with prior/current byte pins and compare-before-replace. Failed acknowledgement is not failure-to-write. A changed project dispatcher cannot accept an old result, and cannot bypass an outstanding target operation by generating a new request ID.
4. **Receipt return:** the privileged executor writes bounded immutable receipts outside the project Store. `upgrade` ingests exact copied bytes through validated bindings and its publication fence. The handoff lifecycle distinguishes `WAITING_FOR_OPERATOR`, target `UNKNOWN`, `CONFIRMED`, `STALE` and rejection; resumption picks the existing intent/result and next required action. Run phase, source block, original budgets and error history survive the handoff. It advances to the next stage only after independently accepted matching evidence.
5. **Actual verification/admission:** invoke supported native facts/HTTP/browser/isolation/edit/restore tools with pinned producer versions and a declared required-check policy. The present facts adapter is deliberately pilot-specific (HW500 ID1); a fresh-project acceptance needs a reviewed generic receipt with explicit expected identity/baseline policy, rather than weakening that producer invariant. Missing receipts remain NOT_RUN. DEMO_READY becomes a computed outcome of complete current scope/fields/media/features plus mandatory target checks, not “run no longer returns BLOCKED.” The current pilot can remain NOT_READY for unresolved required navigation/media even after orchestration works.
