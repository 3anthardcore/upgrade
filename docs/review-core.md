# Независимая проверка ядра, 29 сентября 2026

Область: `packages/core/index.ts`, `packages/core/pipeline.ts`, `packages/verifier/index.ts`, существующие unit/integration tests. Исходники только прочитаны; отдельные регрессионные тесты добавлены в `tests/unit/core-review.test.ts`. Замечания относятся к прочитанной версии и требуют повторной проверки после интеграции.

1. **P1 — heartbeat снимает абсолютное ограничение времени задачи.** `heartbeatTask` устанавливает `lease_until = now + min(ttl, max_seconds)` при каждом вызове. Задача с `max_seconds:1` может через 0,9 секунды получить ещё одну секунду и публиковать через 1,1 секунды. Повторение позволяет работать без предела. Нужно сохранять начало/deadline текущей попытки и ограничивать все heartbeat абсолютным deadline. Адаптер Codex имеет собственный timeout, но этот публичный контракт ядра используется и другими исполнителями. Регрессия: `heartbeats cannot extend...`.

2. **P1 — произвольный статус через публичное ядро.** `setRunStatus(string)` принимает `DEMO_READY`, `PRODUCTION_READY`, `LIVE_VERIFIED` и любой неизвестный текст без проверок. Нынешний reporter всегда отдаёт NOT_READY, поэтому сквозной ложной готовности не обнаружено; но `getStatus().run.execution_status` уже содержит неподтверждённую готовность. Setter операционного статуса должен иметь строгий allowlist; readiness должна иметь отдельный доказательный gate. Регрессия: `generic status setter...`.

3. **P1 — ложное завершение асинхронного этапа.** `runStage` пишет `stage.completed` сразу после получения Promise из callback. Последующий reject не создаёт `stage.failed`. Для HTTP/браузерных/импортных операций это недостоверный аудит после сбоя. Операция должна await callback, затем сохранить завершение или ошибку. Регрессия: `async stage failure...`.

4. **P2 — потеря dispatcher ownership обнаруживается после операции.** `Pipeline.locked` выставляет `lost`, но продолжает `fn`; проверка выполняется после всех побочных эффектов. `phase`, `save` и ядро публикации не проверяют token владельца. После истечения блокировки второй dispatcher может начать работу, а первый ещё сохранять стадии/артефакты. Нужны fencing для записей pipeline и отмена активной операции при потере ownership; одного локального bool недостаточно. Тест: украсть истёкший dispatcher lease между загрузкой и публикацией, запретить запись прежнего владельца.

5. **P2 — истёкшая задача остаётся RUNNING при исчерпанном бюджете.** Перенос reserved → unknown в `claimTask` находится в одной транзакции с проверкой нового бюджета. Если бюджет нового attempt исчерпан, rollback отменяет также фиксацию истечения lease. Дополнительная работа запрещена правильно; но состояние и расходы не отражают неизвестный результат предыдущего worker. Разделить сверку истёкших попыток и резервирование нового attempt. Тест: лимит 1, истёкшая задача, retry запрещён; задача больше не RUNNING, reserved=0, unknown=1 и событие истечения сохранено.

6. **P2 — сетевой timeout не является общим deadline.** `verifyRoutes` ждёт `safeFetch`; в нём используется inactivity timeout socket, который сбрасывается при каждом фрагменте ответа. Медленный поток может удерживать запрос существенно дольше лимита. Для внешнего сайта нужен абсолютный AbortSignal/deadline, включая DNS, и общий бюджет проверки. Это также касается crawl callback, где budget проверяется между запросами. Тест: сервер посылает байт каждые несколько миллисекунд; запрос обязан завершиться по общему timeout, даже когда socket активен.

Верные ограничения: verifier использует исходный scope в знаменателе, missing routes становятся FAIL, непроведённые проверки Битрикс/медиа/браузера/восстановления остаются NOT_RUN; reporter и pipeline не выставляют DEMO_READY. Проверка title/H1/description/main намеренно ограничена HTTP-smoke, не подтверждает перенос всех фактических полей — это отражено отдельным NOT_RUN.

Команда регрессий: `node --disable-warning=ExperimentalWarning --test tests/unit/core-review.test.ts`. Фактический исход до исправления: **0 PASS, 3 FAIL**, exit code 1; все три дефекта воспроизведены. Первый тест: missing expected exception после истечения task budget; второй: неподтверждённый DEMO_READY принят; третий: ранний stage.completed. Следующий шаг — исправления владельцем core, затем запуск этого набора и всего `npm test`. Это исходный результат независимого review, а не итоговое состояние после исправлений.
