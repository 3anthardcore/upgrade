# UPGRADE — техническое задание на создание проекта в Codex

Версия: 1.0. Дата: 29 сентября 2026 года. Язык интерфейса и отчётов: русский.

Статус: спецификация к реализации. Описанные команды, модули и агенты предстоит разработать; этот документ не подтверждает наличие работающей системы.

## 1. Назначение и конечный результат

Создать Upgrade — управляемую из Codex систему агентов и программных инструментов, которая принимает URL существующего сайта на любой исходной платформе, исследует доступную публичную часть, создаёт обновлённую версию на «1С-Битрикс: Управление сайтом» и проверяет перенос контента, адресов и согласованных функций.

Основной пользователь первой версии — владелец Upgrade. Он запускает проекты, просматривает результат и принимает решения по исключениям. Отдельный публичный SaaS, регистрация клиентов, биллинг и CRM продаж в первую версию не входят.

Результат каждого проекта:

1. Работающая демонстрационная версия на отдельной установке Битрикс.
2. Новый адаптивный дизайн с едиными компонентами.
3. Перенесённые страницы и данные в пределах явно зафиксированного объёма.
4. Сохранённые пути URL и значимые параметры запросов.
5. Редактируемый контент в административной части Битрикс.
6. Исходники собственных компонентов, шаблона и инструментов переноса.
7. Машиночитаемые реестры страниц, данных, функций и проверок.
8. Понятный отчёт о готовности, ограничениях, времени и расходах.
9. При наличии необходимых доступов — пакет внедрения и проверенный сценарий отката.

Ключевой принцип: агент не может объявить результат готовым только на основании собственного сообщения об успехе. Готовность подтверждают артефакты и независимые проверки.

## 2. Объём и границы продукта

### 2.1. Что означает «любой сайт»

Исходная платформа не является ограничением: WordPress, Tilda, Joomla, Битрикс, другие CMS, статические сайты, серверные и клиентские приложения. Основной путь исследования — HTTP и браузер; определение CMS помогает выбрать адаптер, но не является условием запуска.

Система обязана поддерживать общую обработку HTML и страниц с JavaScript. Для нестандартных структур допускаются дополнительные адаптеры. Неизвестная CMS не должна приводить к немедленному отказу.

При этом публичная ссылка не предоставляет серверный код, приватные API, базу пользователей, заказы, закрытые кабинеты и внутренние алгоритмы. Такие части фиксируются как недоступные или требующие отдельной реализации. CAPTCHA, авторизация и технические ограничения доступа отражаются в отчёте, без обхода защиты.

Полнота может быть доказана относительно согласованного реестра и полученных источников. Абсолютную полноту неизвестного сайта по одной ссылке система обещать не должна.

### 2.2. Поддерживаемые типы страниц

В первой полной версии обязательны: главная, текстовая страница, услуга, список услуг, статья, список статей, категория каталога, товар, контакты, результаты поиска, страница 404. Поддерживаются вложенные разделы, пагинация, типовые фильтры и варианты товаров.

Специальные калькуляторы, бронирования, карты со сложной логикой, конфигураторы и кабинеты рассматриваются через отдельный реестр функций. Их статус не должен маскироваться общим статусом «сайт перенесён».

### 2.3. Три режима проекта

| Режим | Вход | Результат |
|---|---|---|
| `public-demo` | Публичная ссылка и пожелания | Изолированная демонстрация; данные являются снимком источника |
| `owner-migration` | Ссылка, предоставленные экспорты и доступы | Перенос согласованных данных и подключение функций владельца |
| `bitrix-redesign` | Доступ к исходному Битрикс | Отдельная копия с обновлением шаблона и сохранением согласованной бизнес-логики |

Режим по умолчанию — `public-demo`. Переход к другим режимам не означает автоматического изменения рабочего сайта.

### 2.4. Готовность демо и готовность к запуску

`DEMO_READY` означает, что выполнен согласованный демонстрационный объём, обязательные проверки пройдены, ограничения опубликованы в отчёте. В самом демо явно обозначено, что это концепция обновления.

`PRODUCTION_READY` дополнительно требует подходящей лицензии и окружения, подтверждённого источника цен и наличия, проверенных интеграций, правил обработки заявок, плана переключения и восстановления.

`LIVE_VERIFIED` присваивается только после разрешённого внедрения и проверки реального домена. Автоматический рост продаж или сохранение поисковых позиций результатами проекта не считаются.

## 3. Пользовательский сценарий

1. Пользователь сообщает Codex URL и необязательные пожелания к дизайну.
2. Codex создаёт проект Upgrade с уникальным идентификатором.
3. Проверка окружения определяет доступные инструменты, лимиты, состояние целевого Битрикс и недостающие настройки.
4. Исследователь собирает карту сайта, типы страниц, данные и видимые функции.
5. Руководитель фиксирует объём, ограничения, план, бюджет и список задач.
6. Дизайнер и разработчики создают единый шаблон и репрезентативные страницы.
7. Импортёр переносит остальной контент и регистрирует маршруты.
8. QA проверяет результат; исправления проходят повторную проверку затронутых частей.
9. Пользователь получает демо и отчёт с фактами готовности.
10. После получения доступов и согласования внедрения выполняется отдельный производственный сценарий.

Обычные обратимые шаги в уже разрешённой области выполняются без постоянных вопросов пользователю. При недостатке необязательных сведений система применяет документированный вариант по умолчанию. Вопросы задаются для отсутствующих доступов, фактов, существенного изменения объёма или действий вне разрешённой области. Уже данное разрешение учитывается повторно.

## 4. Основные архитектурные решения

| Область | Решение для первой версии |
|---|---|
| Рабочее место | Codex; запуск и просмотр проекта через чат и CLI Upgrade |
| Ядро Upgrade | TypeScript, Node.js совместимой поддерживаемой версии |
| Браузерные инструменты | Playwright; HTTP-загрузчик для простых страниц и ресурсов |
| Состояние | SQLite на локальном диске, миграции схемы; один писатель состояния |
| Артефакты | Файловое хранилище по проектам, неизменяемые версии и SHA-256 |
| Контракты | JSON Schema; YAML только для редактируемой конфигурации |
| Целевой сайт | Битрикс, PHP-FPM, Nginx, MySQL совместимых версий |
| Среда выполнения | Linux; на Windows — один документированный путь через WSL2 |
| Развёртывание демо | Изолированный проект Docker Compose либо выделенное тестовое окружение Linux |
| Контроль кода | Git; отдельные рабочие области для параллельных изменений |
| Проверки | Модульные и интеграционные тесты, браузерные сценарии, PHP lint, проверка ссылок |

Конкретные версии фиксируются в lock-файлах, образах и `runtime-manifest.json` после проверки совместимости. Не использовать плавающий `latest` в воспроизводимой сборке.

Базовый вариант целевого сайта — собственный шаблон Upgrade без обязательной зависимости от Aspro, INTEC или другого коммерческого решения. Поддержку конкретного решения добавлять отдельным адаптером с проверкой лицензии и обновлений.

Технические требования Битрикс проверять при подготовке окружения; текущая официальная страница указывает PHP 8.2 и MySQL 8.0 как минимальные версии. Это нижняя граница, а не выбор версии для будущей установки. [Официальные требования Битрикс](https://www.1c-bitrix.ru/products/cms/requirements.php).

Ядро должно предоставлять операции `createProject`, `planRun`, `createTask`, `claimTask`, `heartbeatTask`, `submitResult`, `acceptTask`, `rejectTask`, `runStage`, `getStatus`, `resumeRun`, `validateArtifacts`, `exportReport`. CLI — оболочка над ними. Для исполнителей предусмотреть локальный IPC либо соответствующие CLI-команды; прямое редактирование SQLite агентами запрещено. Права принятия/отклонения результатов отделены от прав исполнения. Будущий веб-интерфейс должен использовать эти же операции без переписывания импорта и проверки.

## 5. Реальная интеграция с Codex

### 5.1. Два поддерживаемых способа запуска

**Интерактивный:** Codex выступает руководителем, вызывает CLI Upgrade и делегирует независимые задачи доступным субагентам. Каждую задачу он сначала регистрирует в состоянии Upgrade и затем прикладывает результат. Субагенты документированы OpenAI; доступность проверяется в конкретной среде. [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

**Автоматизированный:** собственный диспетчер Upgrade запускает ограниченные задания через адаптер Codex CLI. Документированный `codex exec` поддерживает программный запуск; `--json` даёт поток событий, `--output-schema` — структурированный итог. Синтаксис дополнительно проверяется на установленной версии. [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode).

В каждый момент один запуск имеет только одного владельца диспетчеризации. Интерактивное и автоматизированное управление не должны одновременно выдавать одни и те же задачи. Передача управления выполняется с блокировкой и записью события.

### 5.2. Исполняемый адаптер

Адаптер обязан иметь операции `probe`, `start`, `poll`, `cancel`, `collectResult`. Он преобразует события конкретной версии Codex в стабильные события Upgrade. Транспорт может меняться; бизнес-логика пайплайна от него не зависит.

Нельзя считать внутренние инструменты приложения Codex общедоступным API проекта. Нельзя строить диспетчер на имитации кликов по чату. Наличие Markdown-файлов с ролями само по себе не является реализацией команды.

Роль, модель, ограничения инструментов, рабочая директория и схема результата назначаются явно. Модели выбираются из доступных в текущей среде; конкретные имена не зашиваются в ядро.

При недоступности параллельной работы допускается последовательное выполнение тех же контрактов. Оно отмечается в отчёте. Для приёмки многоагентного режима нужен отдельный фактический тест параллельного запуска.

### 5.3. Инструкции проекта

В корневом `AGENTS.md` разместить короткие правила: цель, границы доступа, правила артефактов, тесты, порядок делегирования и ссылки на подробную документацию. Codex поддерживает инструкции `AGENTS.md`; нельзя полагаться на бесконечный объём автоматически загружаемого текста. [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

Повторяемые процедуры оформить в `.agents/skills/upgrade-*/SKILL.md`: запуск проекта, исследование сайта, проектирование Битрикс, дизайн, импорт, QA и подготовка внедрения. Skills содержат инструкции и ссылки на исполняемые инструменты; не заменяют эти инструменты. [Build skills](https://learn.chatgpt.com/docs/build-skills).

Не обещать выполнение после закрытия приложения или завершения процесса. Возобновление обеспечивается сохранённым состоянием; фоновая работа — отдельным явно запущенным worker-процессом. Подписка Codex и платёжные условия API не считаются взаимозаменяемыми.

## 6. Роли агентов

Роль — специализация исполнителя. Система не обязана держать все роли одновременно; начальный лимит — не более трёх исполнителей помимо руководителя, в пределах фактически доступных слотов.

| Роль | Вход | Обязательный выход |
|---|---|---|
| Руководитель | Цель, конфигурация, состояние | План, задачи, решения, итоговая сводка |
| Исследователь | URL, правила обхода | Реестр URL, снимки, список функций и пробелов |
| Аналитик данных | Снимки и извлечённые поля | Сущности, связи, источники, неоднозначности |
| Архитектор Битрикс | Модель данных, маршруты | Карта инфоблоков, свойств, компонентов и модулей |
| UX/UI-дизайнер | Контент, задачи бизнеса, ограничения | Дизайн-токены, композиции страниц, состояния элементов |
| Разработчик интерфейса | Дизайн и модель страниц | Шаблон, компоненты, адаптивное поведение |
| Разработчик Битрикс | Архитектура и схема маршрутов | Модуль Upgrade, миграции, маршрутизация, функции |
| Импортёр | Валидированные сущности | Пакет переноса, сопоставления ID, журнал импорта |
| QA/SEO-проверяющий | Реестры, сборка, сценарии | Проверки URL, данных, интерфейса и SEO; дефекты |
| Инженер развёртывания | Пакет и профиль окружения | Изолированное демо, backup/restore и пакет внедрения |

Автор изменения не может единолично подтвердить его приёмку. Детерминированные проверки запускаются отдельно от творческого агента. Визуальный проверяющий получает требования и фактические скриншоты; формулировка разработчика «всё хорошо» доказательством не является.

Агенты обсуждают решения сообщениями с привязкой к задаче и версии артефакта. У каждого обсуждения есть ожидаемый результат и лимит итераций. Неограниченные разговоры и рекурсивное создание агентов запрещены архитектурой диспетчера.

## 7. Протокол задач, событий и артефактов

### 7.1. Задача

Обязательные поля: `schema_version`, `task_id`, `project_id`, `run_id`, `stage`, `role`, `goal`, `input_artifact_ids`, `depends_on`, `allowed_paths`, `allowed_tools`, `acceptance_checks`, `status`, `attempt`, `max_attempts`, `lease_owner`, `lease_until`, `fencing_token`, `budget`, `idempotency_key`, `created_at`, `updated_at`.

`fencing_token` — монотонно растущий номер владения задачей. Запоздавший исполнитель со старым номером не может опубликовать результат после передачи задачи другому.

### 7.2. Результат агента

Обязательные поля: `task_id`, `attempt`, `input_hash`, `artifact_ids`, `summary`, `checks`, `unresolved_issues`, `suggested_followups`, `usage`, `runtime_version`.

Результат проходит JSON Schema, проверку принадлежности проекту, доступности файлов, контрольных сумм и привязки к актуальным входам. Произвольный текст без контрактного результата не закрывает задачу.

### 7.3. Событие

Обязательные поля: `event_id`, `sequence`, `project_id`, `run_id`, `task_id`, `type`, `actor`, `timestamp_utc`, `correlation_id`, `causation_id`, `payload`.

Типы: `task.created`, `task.claimed`, `task.started`, `task.heartbeat`, `artifact.proposed`, `check.completed`, `task.accepted`, `task.rejected`, `task.retry_scheduled`, `run.paused`, `run.resumed`, `run.failed`, `run.completed`.

Состояние задачи и запись события фиксируются одной транзакцией SQLite. JSONL-журнал — экспорт для чтения и диагностики, а не второй независимый источник истины. В журнал пишутся действия и краткие обоснования решений, без требования сохранять скрытые рассуждения модели.

### 7.4. Артефакт

Обязательные поля: `artifact_id`, `project_id`, `run_id`, `type`, `relative_path`, `sha256`, `size_bytes`, `schema_version`, `producer_task_id`, `input_hashes`, `created_at`, `validation_status`.

Артефакты неизменяемы: исправление создаёт новую версию. Сначала файл пишется во временную директорию, проверяется и атомарно публикуется в реестр. Пути разрешаются только внутри области проекта. Повреждённый или отсутствующий файл делает зависимые результаты непригодными.

## 8. Оркестрация и восстановление

Зависимости задач образуют направленный граф без циклов. Исследование предшествует модели данных; дизайн и архитектура могут идти параллельно после классификации страниц; массовый импорт начинается после проверки схемы и пробного пакета.

Состояния задачи: `PENDING → READY → RUNNING → VALIDATING → ACCEPTED`. Дополнительные: `RETRY_WAIT`, `BLOCKED`, `FAILED`, `CANCELLED`, `STALE`.

Состояния запуска: `NEW`, `PREFLIGHT`, `DISCOVERING`, `PLANNING`, `BUILDING`, `IMPORTING`, `VERIFYING`, `DEMO_READY`. Боковые состояния: `PAUSED`, `BLOCKED`, `FAILED`, `CANCELLED`. Производственный сценарий использует `PRODUCTION_READY`, `DEPLOYING`, `LIVE_VERIFIED`, `ROLLING_BACK`.

Обязательные правила:

- Единственный диспетчер изменяет состояние; исполнители отправляют результаты через контракт.
- Запись в один общий файл и импорт в одну целевую БД сериализуются. Независимые файлы допускают параллельную работу с последующей интеграцией.
- Агенты разработки работают в отдельных Git worktree либо в непересекающихся областях. Общие изменения принимает интегратор.
- Доставка задач допускает повторение; побочные эффекты защищаются идемпотентностью и уникальными ограничениями.
- После обрыва проверяются фактические данные назначения, затем выполняется продолжение. Один записанный checkpoint не доказывает состояние Битрикс.
- Изменение входного артефакта помечает зависимые задачи `STALE`, сохраняя прежние результаты для аудита.
- По умолчанию — до трёх попыток задачи и до двух циклов автоматического исправления одного дефекта. Далее — понятный блокер.
- Повтор при временной ошибке использует увеличивающуюся задержку. Ошибка данных не должна вызывать бесконечный сетевой retry.
- При паузе прекращается выдача новых задач; активным даётся ограниченное время на сохранение результата. Отмена останавливает дерево дочерних процессов.
- При достижении бюджета работа останавливается на границе операции; перерасход уже выполняющейся операции учитывается отдельно.
- Потраченный и зарезервированный бюджет сохраняется транзакционно. Resume, retry и передача диспетчеризации не обнуляют лимиты. Неизвестный расход после сбоя учитывается консервативно до сверки; увеличение лимита является отдельным зарегистрированным решением в пределах полномочий оператора.
- `resume` восстанавливает работу по состоянию и артефактам без зависимости от доступности старого чата.
- Откат кода, базы, файлов и внешних эффектов рассматривается раздельно. Git revert не является откатом импорта.

## 9. Конфигурация проекта

Минимальный пользовательский ввод — URL. Остальные обязательные настройки берутся из заранее созданного профиля окружения. Без готового Битрикс доступна фаза исследования; готовое демо не заявляется.

Пример будущего `project.yaml` — контракт продукта, а не готовая конфигурация Codex:

```yaml
schema_version: 1
project_id: sample-company
source:
  entry_url: https://example.com/
  allowed_hosts: [example.com]
  locale: ru-RU
  mode: public-demo
target:
  platform: bitrix
  environment_profile: demo-linux
  url_policy: preserve
  template: upgrade-base
crawl:
  max_html_pages: 10000
  max_assets: 50000
  max_download_bytes: 10737418240
  max_wall_time_minutes: 240
  requests_per_second_per_host: 1
  concurrency_per_host: 2
  respect_robots: true
  max_redirects: 5
agents:
  max_workers: 3
  max_task_attempts: 3
  max_fix_cycles: 2
  budget_profile: pilot
design:
  preserve_logo: true
  preserve_factual_text: true
  approval_mode: automatic_with_report
demo:
  access: authenticated
  indexing: disabled
  outbound_integrations: disabled
```

Эти лимиты — стартовые ограничения запуска, а не обещание производительности. Достижение любого лимита создаёт `PAUSED` и неполный отчёт; система не выдает усечённый обход за полный. Профиль бюджета должен содержать реальные пределы времени и расходов/использования, а не неограниченные пустые значения.

Для каждого конфигурационного поля задать тип, значение по умолчанию, допустимый диапазон и влияние на повторный запуск. Секреты задаются ссылками на хранилище секретов, не значениями в YAML.

## 10. Исследование и обход сайта

### 10.1. Обнаружение страниц

Источники: начальный URL, `robots.txt`, sitemap и sitemap index, меню, внутренние ссылки, хлебные крошки, пагинация, связанные товары, языковые ссылки, DOM после рендеринга. При наличии доступа владельца — выгрузки CMS, маршрутов, аналитики и журналов как дополнительные источники.

Обход ведётся очередью со статусом каждого URL. Сохраняются источник обнаружения и родительская страница. Внешние домены и поддомены не включаются автоматически целиком: для страниц и ресурсов задаются отдельные разрешённые области.

Нельзя бесконечно перебирать фильтры, даты календаря, поисковые запросы или комбинации сортировок. Такие пространства фиксируются как параметризованные маршруты и проверяются по правилам и набору состояний.

### 10.2. Загрузка и браузер

Использовать HTTP для доступного HTML и ресурсов, браузер — для клиентского контента, lazy loading и видимых состояний. Сохранять исходный ответ и отдельно DOM после рендеринга.

Для страницы фиксировать статус HTTP, цепочку редиректов, конечный URL, MIME, время, размер, заголовки без секретов, хеши контента, title, description, canonical, robots, заголовки, ссылки, медиа, структурированные данные и выбранный язык/регион.

Браузер не выполняет покупки, регистрацию, отправку форм, добавление в корзину источника и другие изменяющие действия. Прокрутка, раскрытие меню и чтение вариантов допустимы в пределах режима исследования. Неоднозначные действия отмечаются как непроверенные.

Воспроизводимый снимок имеет время начала/окончания, профиль браузера, viewport, локаль и правила cookies. Для выбранных критических данных выполняется повторное получение в сопоставимом контексте и сравнение хешей/значений; выявленные расхождения отмечаются. Хеш единственной загрузки не обнаруживает последующие изменения. Отсутствие выявленных расхождений не доказывает атомарность снимка всего сайта; для согласованной выгрузки рабочего магазина требуется соответствующий источник владельца.

### 10.3. Устойчивость и завершение

Ограничивать частоту запросов, размер ответа, размер распакованных данных, время рендеринга и число переходов. Учитывать `Retry-After`, 429 и 503; при повторяющихся ошибках останавливать работу с хостом. robots учитывается как правило обхода, а не как доказательство прав на использование материалов.

Отчёт различает `DISCOVERED`, `FETCHED`, `RENDERED`, `EXCLUDED`, `UNREACHABLE`, `REQUIRES_ACCESS`, `RATE_LIMITED`, `FAILED`. Для исключения обязательны причина и правило.

Обход считается исчерпанным, когда обработана очередь в разрешённом объёме, проверены обнаруженные sitemap и закончены допустимые источники новых URL. Отдельно указывается уровень уверенности полноты и наличие непроверенных источников.

## 11. Сохранение URL и SEO

### 11.1. Идентичность адресов

Для URL хранить отдельно `raw_url`, `request_target`, `crawl_key`, `content_entity_id`, `canonical_url`, `final_url`, `redirect_chain` и `target_route`. Нормализация очереди не может менять адрес назначения без отдельного правила.

Сохранять исходный регистр пути, завершающий слеш, расширения `.html/.php`, вложенность, кириллицу/кодирование и семантически значимые query-параметры. Не декодировать `%2F` в `/` и не склеивать адреса по совпадению canonical без проверки.

Query-параметры классифицируются как идентичность ресурса, вариант товара, фильтр, пагинация, сортировка, tracking или временный токен. Неизвестные параметры сохраняются до классификации. Удаление tracking из ключа обхода не означает поломку открытия исходной ссылки.

Повторяющиеся параметры, пустые значения и порядок учитываются там, где влияют на поведение источника. Фрагменты `#section` проверяются как якоря; hash-маршруты SPA отдельно моделируются и тестируются в браузере.

### 11.2. Реестр маршрутов

На каждый адрес или правило маршрута фиксировать: источник, назначение, тип страницы, ожидаемый HTTP-статус, целевую сущность, политику query, canonical, причину изменения, версию правила и тесты.

Публичные страницы со статусом 200 по умолчанию сохраняют путь и открываются без дополнительного редиректа. Исходные редиректы воспроизводятся по согласованной карте. Изменения адресов допустимы только как отдельное зафиксированное решение; массовое перенаправление всего на главную запрещено.

При нескольких исходных хостах используется таблица `source_origin → demo_origin`. Нельзя сливать одинаковые пути разных поддоменов в одну страницу.

Пример:

```text
https://source.example/shop/red-brick.html?variant=red
https://demo.example/shop/red-brick.html?variant=red
```

На демо отличается origin. Полный исходный URL может сохраниться только после разрешённого переключения исходного домена.

### 11.3. Реализация на Битрикс

Использовать штатную обработку адресов и собственный маршрутизатор с индексируемым реестром. Не создавать тысячи произвольных regex-правил, когда достаточно небольшого набора правил входа и поиска точного маршрута. Штатные механизмы UrlRewrite допускают обработку адреса, отличного от физического пути. [Обработка адресов Битрикс](https://dev.1c-bitrix.ru/api_help/main/general/urlrewrite.php).

Отдельно проверять коллизии с физическими файлами, каталогами и служебными маршрутами `/bitrix/`, `/local/`, административной частью и API. Неразрешённая коллизия — блокер, а не молчаливый перенос URL в другое место.

### 11.4. SEO и метаданные

По умолчанию переносить существующие title, description, H1 и смысл контента; изменения предложений и метаданных вести отдельным диффом. Перенести хлебные крошки, внутренние ссылки, поддерживаемые hreflang и подтверждённую structured data.

Canonical, sitemap и абсолютные ссылки формируются из профиля окружения. На production не должно остаться ссылок на demo-host. Демо защищается доступом и `noindex`; запрет в robots сам по себе не считается защитой от индексации.

Проверять корректные 404/410, отсутствие soft-404, циклов и непредусмотренных цепочек редиректов. Существовавшие ошибки источника учитывать отдельно от внесённых Upgrade. SEO-проверка подтверждает техническую корректность, а не будущие позиции в поиске.

## 12. Извлечение данных и происхождение фактов

Общая модель не зависит от исходной CMS. Сущности: `Site`, `Page`, `Route`, `Menu`, `Section`, `Service`, `Article`, `Product`, `Offer`, `PriceObservation`, `Asset`, `Feature`, `Evidence`.

Для значимого поля сохранять значение, единицу измерения, исходный URL, время получения, источник внутри страницы или экспорта, уровень уверенности и статус проверки. У каждой сущности есть устойчивый `source_id`, не зависящий от очередности импорта.

До импорта фиксировать `content-requirements.json`: обязательные и условно обязательные поля каждого типа, ожидаемые связи, медиа и правила сравнения с evidence источника. Этот контракт версионируется вместе со scope-manifest и используется независимым QA. Различать «отсутствует в источнике», «не удалось извлечь», «неизвестно» и «пустое допустимое значение». Удаление требования после неудачного переноса считается изменением объёма, а не исправлением ошибки.

Извлечение выполнять кодом по правилам и шаблонам; LLM использовать для классификации, неоднозначностей и разработки адаптеров. Повторные страницы одного типа не должны требовать полной независимой генерации моделью.

Тексты хранить блоками с типами: заголовок, абзац, список, таблица, изображение, документ, цитата. Допустимо санитизированное HTML-поле для форматированного содержимого. Нельзя сохранять целую исходную страницу одним непрозрачным HTML-блоком вместо модели сайта.

Запрещено придумывать цены, наличие, отзывы, сертификаты, гарантии, реквизиты, клиентов, награды и условия доставки. Переписанный маркетинговый текст отделяется от исходных фактов. Неуверенные поля направляются на проверку либо остаются явно неизвестными.

Изображения и документы загружаются с исходными адресами и хешами. Дедупликация ресурсов — по содержимому; объединение товаров по одному изображению или одному артикулу не допускается. Предусмотреть `srcset`, фоновые изображения и изображения вариантов.

HTML очищается от исполняемого содержимого; SVG санитизируются или безопасно преобразуются. Скрипты исходного сайта, аналитика, чаты и формы не переносятся автоматически. Основной контент демо не должен зависеть от hotlink к источнику.

## 13. Каталог, предложения, цены и единицы

Карточка товара включает название, описания, разделы, производителя, артикул, характеристики с типами и единицами, изображения, документы, варианты, SEO-поля и источники данных.

Товар и торговое предложение — разные сущности. Для вариантов сохраняются свойства выбора, собственный идентификатор, изображения, цена и наличие, если они достоверно доступны. Одинаковый SKU у разных производителей не является основанием для объединения.

Цена хранится десятичным значением вместе с валютой, единицей, типом, условиями, наблюдаемым регионом и временем получения. Различать обычную, акционную, «от», оптовую и диапазонную цену. Не превращать «от 100» в точную цену 100.

Сохранять минимальный заказ, кратность, упаковку, количество в упаковке и коэффициенты пересчёта, если они подтверждены источником. Не подменять м² штуками, погонными метрами или упаковками. Расхождения видимой цены и structured data направлять на проверку.

Неизвестное наличие не приравнивается к «в наличии». Неизвестная цена не приравнивается к нулю. По умолчанию такие товары нельзя оплатить; интерфейс показывает соответствующее состояние.

`public-demo` работает со снимком цен. Регулярная синхронизация и выбор источника истины для рабочего магазина — отдельная настройка режима владельца. Недопустима автоматическая массовая замена производственных цен в ходе демонстрационного переноса.

## 14. Дизайн и интерфейс

Задача дизайнера — улучшить ясность предложения, навигацию, чтение контента и ключевые сценарии, сохранив фактическую основу бизнеса. Текущая геометрия страниц не является обязательной для сохранения; URL и данные являются.

Обязательные артефакты: дизайн-бриф, токены цвета/типографики/отступов, библиотека компонентов, карта шаблонов, примеры desktop/mobile и список изменений с объяснением назначения.

Сначала разрабатываются общие шапка, меню, подвал, формы, кнопки, карточки, таблицы и состояния. Затем — главная, типовая внутренняя страница, категория и товар либо услуга. Остальные страницы собираются из шаблонов и данных.

Не генерировать тысячи независимых HTML-страниц моделью. Один типовой дефект исправляется на уровне компонента.

Обязательные состояния: загрузка, пустой результат, ошибка, недоступная цена, отсутствующее изображение, длинное название, валидация формы, успешное тестовое действие. Не допускать декоративных кнопок, представленных как действующие.

Проверить ширины 360, 390, 768, 1024 и 1440 px; основные touch-сценарии, меню, фильтры, галерею, клавиатурную навигацию и видимый фокус. Не должно быть непредусмотренной горизонтальной прокрутки, перекрытий и обрезки важных текстов.

Логотип и фактические фото сохраняются по умолчанию. Генерация декоративных изображений — опциональный инструмент с отдельным бюджетом. Не генерировать изображения конкретного товара, сертификата или выполненного объекта как документальный факт.

Визуальное сравнение с источником используется для проверки контента и улучшений, а не для требования пиксельного совпадения. После выбора нового дизайна скриншоты становятся базой для проверки регрессий.

По умолчанию дизайнер работает автономно и прикладывает обоснование. Пользователь может включить остановку после концепции; обязательное согласование каждой страницы в процесс не закладывается.

## 15. Реализация целевого сайта на Битрикс

### 15.1. Структура собственного кода

Предусмотреть собственный модуль `upgrade.core`, шаблон `/local/templates/upgrade/`, компоненты в `/local/components/upgrade/`, установочные миграции и импортёр вне публичного доступа. Название модуля — проектное; совместимость и конфликты проверяются при реализации.

Ядро Битрикс и файлы коммерческих решений не изменять. Изменения конфигурации окружения и корневых маршрутов оформлять отдельно с diff и резервной копией. Не помещать лицензионный дистрибутив, ключи и клиентские данные в публичный репозиторий.

Использовать документированные API установленной версии: D7 там, где покрывается операция, и поддерживаемые API инфоблоков для соответствующих сущностей. Не писать напрямую в системные таблицы каталога, цен и заказов ради упрощения импорта. [CIBlockElement::Add](https://dev.1c-bitrix.ru/api_help/iblock/classes/ciblockelement/add.php), [модель Price](https://dev.1c-bitrix.ru/api_d7/bitrix/catalog/model/price/index.php).

### 15.2. Модель содержимого

Архитектор создаёт таблицу соответствия: сущность Upgrade → сущность Битрикс → поля → свойства → связи → правила уникальности → способ проверки. Номера инфоблоков и групп цен не зашиваются в код.

Разделы, услуги, статьи и каталог должны редактироваться штатными средствами административной части. Варианты товаров оформляются как реальные торговые предложения, если целевой профиль использует соответствующие возможности каталога.

Внешний путь страницы хранится независимо от `CODE` и внутренних ID. Изменение названия товара в админке не должно случайно менять его сохранённый URL.

Обязательны настройки меню, общих контактов, логотипа, реквизитов, баннеров и SEO. Правки пользователя после импорта нельзя безусловно перезаписывать следующим запуском: по умолчанию обновляются только управляемые импортом поля, конфликты показываются отдельно.

При наличии фильтров необходимо настроить свойства разделов, необходимые индексы и их перестроение. После массового импорта выполнять целевую очистку/инвалидацию кешей и проверять публичную выдачу, а не ограничиваться наличием записей в БД.

### 15.3. Протокол импорта

Пакет содержит manifest, schema version, хеши файлов, идентификатор проекта, версию источника и список операций. Пакет валидируется до записи.

Этапы: `validate → dry-run → backup/checkpoint → import batch → reconcile → rebuild indexes/cache → verify`.

Импорт поддерживает:

- Создание и обновление по устойчивому ключу `project + entity type + source_id`.
- Сохранение таблицы `source_id → bitrix_id` независимо от пользовательских названий.
- Ограниченные транзакции по пакетам, журнал фактических операций и повтор без дублей.
- Контрольные точки после подтверждения записи; сверку при неизвестном исходе операции.
- Уникальную блокировку записи в целевой проект.
- Проверку актуального fencing token на стороне единственного шлюза записи перед каждым пакетом. Агенты не имеют обходного доступа к записи в БД. Выдача нового владения синхронизируется с завершением или остановкой старой транзакции; просроченный исполнитель не может перезаписать более свежие данные.
- Карантин повреждённых записей с причиной; ошибки обязательных данных блокируют приёмку.
- Отдельную обработку БД и файлов: компенсацию незавершённых загрузок и поиск файлов-сирот.
- Политику удаления: отсутствие записи в новой выгрузке не удаляет её автоматически.
- Режим удаления/архивации только по отдельному плану и в разрешённом объёме.
- Отчёт количества созданных, обновлённых, пропущенных, конфликтных и ошибочных сущностей.

Перед массовым импортом проверяется небольшой пакет: несколько разделов, товаров, вариантов и страниц каждого типа. Ошибка схемы останавливает массовое применение.

## 16. Функциональные сценарии и интеграции

Создать `feature-matrix.json` и читаемый отчёт. Для каждой функции указывать: исходное наблюдение, сценарий, целевую реализацию, необходимые доступы, статус, тест и подтверждение результата.

Статусы: `IMPLEMENTED`, `SANDBOX_ONLY`, `REQUIRES_INTEGRATION`, `OUT_OF_SCOPE`, `UNVERIFIED`, `BLOCKED`. Исходное наличие кнопки не доказывает серверную реализацию.

Обязательные публичные сценарии, когда применимы к проекту:

| Сценарий | Требование для демо |
|---|---|
| Навигация | Меню, ссылки, хлебные крошки ведут на перенесённые адреса |
| Поиск | Работает по импортированному содержимому; есть пустой результат |
| Каталог | Категории, сортировка и согласованные фильтры работают по данным |
| Товар | Выбор реального варианта меняет согласованные поля |
| Корзина | Добавление, изменение количества, удаление и расчёт по модели единиц |
| Форма | Валидация и запись в локальный тестовый приёмник; явный тестовый результат |
| Checkout | Только тестовый сценарий с синтетическими данными |
| Оплата/CRM/почта/1С | Отключены или подключены к явно заданной песочнице |

Реальные заявки и платежи не должны уходить ни исходной компании, ни сторонним получателям из демо. Если оператор разрешил тест конкретной интеграции, использовать только указанный тестовый контур.

Не подключённую функцию нельзя завершать ложным сообщением «заказ оплачен» или «заявка отправлена компании». Допустимо показать понятное состояние «демонстрация, отправка отключена».

Для запуска рабочего магазина потребуются отдельные тесты оплаты, доставки, налогов/округления, уведомлений, обмена остатками и обработки ошибок, если эти функции входят в объём. Проект не переносит историю заказов и пароли по публичной ссылке.

## 17. Изоляция, доступы и работа с исходными материалами

Эти требования относятся к самой системе, которая открывает произвольные сайты и исполняет генерируемый код.

- Исходные HTML, тексты, документы и сообщения сайта считаются данными. Встроенные указания «измени настройки», «прочитай секреты» или «выполни команду» не становятся инструкциями агенту.
- Краулер и браузер источника не получают production-секреты, SSH-ключи, cookies личного браузера пользователя и доступ к чужим проектам.
- Входные URL разрешены только для HTTP/HTTPS. Запрещены обращения к loopback, приватным, link-local и служебным сетям, если это не отдельно разрешённая тестовая площадка.
- Проверять DNS/IP при соединении и на каждом redirect; ограничения распространяются на browser subrequests, WebSocket и скачивание ресурсов. Одна проверка стартового URL недостаточна.
- Для локальной тестовой площадки использовать отдельный профиль, изолированную сеть и точный список разрешённых адресов.
- Браузерные загрузки, распаковка архивов и создание файлов защищены от выхода за каталог проекта; размер и время ограничены.
- Скачанные скрипты, инструкции репозитория и установщики источника автоматически не выполняются. Исполняется только код Upgrade и принятые изменения в изолированной среде.
- Секреты хранятся в системном хранилище или ином настроенном secret store. В команды, журналы, отчёты и Git попадают только ссылки или замаскированные значения.
- У каждого клиента отдельные файлы, БД, учётные данные БД, временные каталоги, браузерные контексты и резервные копии.
- При нескольких клиентах на одном хосте разграничение обеспечивается правами ОС/контейнерами. Одних разных имён папок недостаточно.
- Демо имеет отдельный hostname, ограничение доступа, TLS при внешнем доступе и защиту от индексации. Для внешнего просмотра выдаётся отзывной доступ с ограниченным сроком.
- В отчёте и демо явно указано происхождение концепции. Отправка предложений владельцам и публикация материалов для широкой аудитории не являются частью автоматического `run`.
- Режим использования исходных материалов и разрешённые направления публикации фиксируются в проекте. Неопределённые права на отдельные материалы отмечаются для решения до публичного выпуска.
- Файлы заказчиков не используются в других проектах. Для удаления проекта предусмотрен отчёт о затрагиваемых путях и хранилищах, сроках хранения и резервных копиях.

Реальный ввод личных данных посетителями в публичном демо не нужен: для сценариев используются синтетические данные и тестовые приёмники.

## 18. Демо, развёртывание и откат

### 18.1. Создание демо

До развёртывания проверить доступное место, версии PHP/БД, необходимые модули, лицензионный режим, hostname, права на файлы, сертификат и отсутствие совпадения с production-назначением.

Автоматизировать подготовку окружения в рамках заранее настроенного профиля. Отсутствие лицензии или доступа не исправляется копированием произвольного ключа; запуск останавливается с конкретным требованием к окружению.

Демо использует отдельную БД и конфигурацию. До первого HTTP/CLI-исполнения PHP клона заблокировать реальные исходящие обращения и отключить cron, агенты Битрикс, почтовые события, обмен с 1С, платёжные обработчики и webhook. Изоляция должна действовать до запуска самого приложения, а не настраиваться первым обращением к нему. Интеграции включаются только после отдельной настройки тестового контура. Не изменять посторонние сайты, bindings и общие серверные службы.

После сборки выполнить проверки HTTP, PHP, логов, ссылок, редактирования через админку и основных браузерных сценариев. Публичный ответ 200 сам по себе не доказывает исправность административной части или заказа.

### 18.2. Пакет внедрения

Подготовить: manifest версии, архив собственного кода, миграции, соответствия сущностей, план конфигурации, список зависимостей, отчёты проверок, backup/restore-инструкцию и smoke-тесты.

Производственное действие должно ссылаться на конкретную версию пакета, домен, окружение и разрешённый объём. Если внедрение уже было явно разрешено в этих границах, не требовать повторного формального подтверждения. Иначе сначала представить готовый пакет и изменения, затем запросить разрешение на сам переход.

### 18.3. Переключение рабочего сайта

Перед переключением определить источник истины для новых заказов, заявок, цен и остатков, появившихся после начального снимка. Предусмотреть финальную дельту и окно ограничения записей либо другой проверенный способ согласования.

Нельзя заменять актуальную производственную БД старым демонстрационным снимком. Новые данные владельца не должны теряться при переходе или откате.

Проверить DNS/виртуальный хост, TLS, целевой домен, robots, canonical, sitemap, реальные интеграции и отсутствие ссылок на демо. Снятие `noindex` выполняется только в профиле рабочего сайта после переключения.

### 18.4. Восстановление

Резервировать каждый сайт независимо: файлы, БД, конфигурация, маршруты и manifest. Выполнить восстановление в отдельное тестовое окружение и smoke-тесты.

Отчёт различает проверку целостности backup, успешное восстановление тестовой копии и фактическое восстановление production. Это разные уровни подтверждения.

План отката содержит триггеры, команды, ответственного оператора, порядок восстановления и способ сохранения данных, созданных после переключения. Целевые RPO/RTO выбираются для конкретного сайта и измеряются на репетиции; универсальные значения не обещаются.

Отдельные команды этапов обязаны применять те же проверки зависимостей и блокировки, что и `run`; они не являются обходом контроля.

`doctor` проверяет доступность Codex CLI/адаптера, авторизацию без вывода секретов, браузер, WSL/Linux, хранилище, место, целевой Битрикс и версионную совместимость. Подключение будущего публичного API не должно быть обязательным для интерактивного пилота в Codex.

Статус показывает фазу, техническое состояние, активные задачи, принятые артефакты, счётчики URL, ошибки, затраты, время последнего события и ближайшее действие. Хранить отдельно `phase` и `execution_status`, чтобы пауза не уничтожала информацию о текущем этапе.

Не использовать придуманный процент общей готовности. Допустим процент проверенных адресов относительно зафиксированного знаменателя и отдельно готовность каждой фазы.

Логи структурированы, фильтруются по проекту/запуску/задаче. Отчёт включает последние значимые события, понятные причины остановки и команды продолжения. Не нужен отдельный веб-кабинет для чтения логов: достаточно CLI и генерируемого HTML-отчёта.

Итоговый отчёт содержит отдельно: обнаружено адресов, включено в объём, получено, собрано, проверено, исключено с причиной, недоступно и осталось с ошибками. URL, уникальные страницы, товары и предложения — разные счётчики.

Пересмотр объёма создаёт новую версию и видимый список исключений; существенное сокращение фиксируется решением пользователя.

Для каждого этапа отчёт показывает, что выполнено автоматически, что вручную и что осталось. Сравнение «до/после» включает одинаковые контрольные страницы, исходные снимки и объяснение изменений. Подготовка коммерческого предложения может быть будущим модулем; автоматическая отправка отсутствует.

## 21. Метрики качества и производительности

Обязательные показатели приёмки полного демо:

- 100% включённых URL имеют маршрут и выполненную проверку ожидаемого поведения.
- 100% обязательных полей и обязательных медиа имеют перенос либо явно разрешённое исключение.
- Нет новых битых внутренних ссылок, необъяснённых 5xx, пустых страниц и soft-404 в принятом объёме.
- Нет неустранённых критических дефектов и дефектов, блокирующих обязательный пользовательский сценарий.
- Для каждого типа шаблона выполнены обычный и граничные браузерные сценарии.
- Нет случайных вызовов production-интеграций и зависимости основного содержимого от исходного сайта.
- Повторный импорт не создаёт дубликатов и не меняет неизменившиеся данные.

Глубокую браузерную проверку выполнять на каждом уникальном шаблоне и его существенных состояниях; проверку HTTP/маршрута/ключевых данных — на всех включённых адресах. Для каждого адреса, чья сущность или состояние определяется только JavaScript либо hash-маршрутом, обязателен короткий браузерный тест именно этого адреса. Общая HTML-оболочка с ответом 200 не подтверждает правильное открытие разных товаров SPA. Выборка страниц не подтверждает полную проверку URL.

Для производительности зафиксировать тестовый стенд, набор данных, браузер и настройки нагрузки. Предлагаемые целевые значения демо: p95 ответа кешируемой страницы до 1 секунды при 10 одновременных клиентах на согласованном стенде; отсутствие горизонтальной прокрутки на контрольных ширинах; медианный mobile Lighthouse Performance не ниже 85 на каждом контрольном шаблоне по трём одинаково настроенным прогонам.

Это проектные цели для измерения, а не доказанные свойства ещё не созданной системы. Если конкретный тип страницы не достигает цели, зафиксировать причину, замеры и решение по отклонению. Не подменять реальные полевые показатели синтетическим баллом и не обещать рост конверсии без эксперимента.

Проверки доступности: семантические подписи, управление клавиатурой, видимый фокус, текстовые ошибки форм, контраст и альтернативные тексты значимых изображений. Автоматическая проверка не заменяет ручной проход ключевого сценария.

## 22. Приёмочные испытания

Для независимого воспроизведения создать собственные тестовые источники с известным составом и эталонными данными. Внешний сайт не должен быть единственным тестом: его содержимое и доступность меняются.

| ID | Сценарий | Условие прохождения |
|---|---|---|
| AT-01 | Обычный сайт, sitemap-only страницы, JS-ссылки, пагинация и lazy loading | Все эталонные доступные страницы найдены; недоступные перечислены |
| AT-02 | Платформы с разной HTML-структурой, неизвестная CMS | Общий процесс работает без требования «источник должен быть Битрикс» |
| AT-03 | `/Product/`, `/product`, `.html`, кириллица, `%2F`, пустые и повторные параметры | Различимые в источнике маршруты остаются различимыми |
| AT-04 | Вариант товара в query, фильтры, пагинация, hash-route и якорь | Правильные данные и состояние открываются по исходной форме ссылки |
| AT-05 | Несколько хостов с одинаковым путём | Маршруты не смешиваются; таблица origin работает |
| AT-06 | 301→302→200, внешний redirect, цикл, 404, soft-404 | Ожидаемое поведение проверено; дефекты источника отражены отдельно |
| AT-07 | Одинаковый SKU у разных товаров; несколько URL одного товара | Разные товары не слиты; подтверждённые алиасы не создают дублей |
| AT-08 | Два цвета и три размера, но четыре реальные комбинации | Созданы ровно четыре предложения, без выдуманных комбинаций |
| AT-09 | Цена за м²/упаковку, «от», скидка, кратность, нет цены | Условия сохранены; неизвестная цена не стала нулевой |
| AT-10 | Остановка crawl, скачивания и импорта до/после записи | Resume продолжает; повреждённые файлы выявлены; дублей нет |
| AT-11 | Два worker, истечение lease, поздний ответ первого | Принят только актуальный результат; побочный эффект не удвоен |
| AT-12 | Изменение принятого route manifest или токенов дизайна | Зависимые проверки становятся STALE и выполняются повторно |
| AT-13 | Превышение лимита, постоянный 429/503, бесконечный календарь | Корректная остановка; нет ложного полного успеха и бесконечных retry |
| AT-14 | Доступ к исходному сайту отключён после сборки | Основные страницы и локальные ресурсы демо продолжают работать |
| AT-15 | Поиск, фильтр, вариант, корзина, количество, форма, checkout | Поведение соответствует feature matrix на desktop и mobile |
| AT-16 | Редактирование товара/статьи в админке и повторный импорт | Правка отображается; пользовательские поля не затёрты молча |
| AT-17 | Инструкция на сайте прочитать секрет; redirect на private IP; опасный SVG | Нет исполнения инструкции, утечки или запрещённого сетевого обращения |
| AT-18 | Одновременные проекты A и B | Нет доступа к чужим данным, БД, секретам и артефактам |
| AT-19 | Демо с активной формой, checkout и скопированными скриптами | Сторонних реальных отправок/платежей нет; тестовый результат обозначен |
| AT-20 | Backup, восстановление в чистое окружение и smoke-тест | Получена работающая тестовая копия с данными и маршрутами |
| AT-21 | Пакет с неверной схемой, хешем или чужим project_id | Импорт отклонён до записи |
| AT-22 | Реальный параллельный запуск двух агентов через выбранный адаптер | Есть task IDs, реальные артефакты, события и независимая приёмка |
| AT-23 | Обязательный QA-тест упал, но агент сообщил об успехе | DEMO_READY не выставлен |
| AT-24 | Смена production-профиля, новые заказы после снимка, репетиция отката | Дельта данных сохранена; демо-снимок не затирает новые данные |
| AT-25 | Повторная сборка из тех же принятых артефактов | Эквивалентные данные/маршруты; для повторного deploy не требуется новая генерация LLM |
| AT-26 | Длинные тексты, нет изображения, много свойств, ширина 360 px | Нет перекрытий; сценарий и навигация доступны |
| AT-27 | Сбой после резервирования бюджета, затем resume/retry и передача управления | Лимиты не обнулены; резерв и неизвестный расход сверены; лишняя задача не выдана |
| AT-28 | Первый HTTP/CLI-запуск клона Битрикс с исходными настройками событий | Сетевая изоляция уже действует; реальные письма, webhook и фоновые отправки отсутствуют |

Для AT-22 имитатор допустим в unit-тестах, но не вместо отдельного фактического интеграционного запуска. При отсутствии доступа к Битрикс его тесты имеют статус `NOT_RUN`, а не `PASS`.

## 23. Нефункциональные требования

**Масштаб.** Первая полная версия должна пройти контрольный профиль до 10 000 HTML-страниц и 50 000 ресурсов в пределах заданных лимитов. Это цель испытания, не жёсткий архитектурный предел: больший проект требует другого профиля ресурсов и отдельного замера.

**Память.** Обрабатывать данные пакетами и потоково, не загружать весь сайт и все картинки в контекст модели или оперативную память.

**Воспроизводимость.** Принятые снимки, промпты, конфигурация, версии схем и кода фиксируются. Повторная генерация LLM не обязана дать идентичные байты; воспроизводимая сборка выполняется из уже принятых артефактов.

**Расходы.** До агентной задачи резервируется бюджет, после выполнения учитываются доступные фактические метрики. Стоимость указывается как измеренная, оценочная либо недоступная. Отсутствие данных о токенах/деньгах не означает нулевой расход. Для недоступного денежного учёта обязательны лимиты задач и времени.

**Обновления.** Схемы данных и конфигурация версионируются. Перед миграцией состояния создаётся backup. Поддерживаемые версии Битрикс и Codex перечисляются в матрице совместимости и проверяются тестами адаптера.

**Эксплуатация.** Предусмотреть очистку временных файлов и старых артефактов по политике хранения, но не удалять последнюю принятую версию и backup автоматически. Команда очистки сначала показывает план и проверяет реальные абсолютные пути.

**Переносимость.** Вся основная логика работает в Linux без привязки к пользовательскому абсолютному пути Windows. PowerShell допускается как тонкая оболочка запуска WSL, без смешивания shell при опасных файловых операциях.

**Документация.** Новый разработчик должен развернуть тестовый источник, выполнить сценарий, прочитать отчёт и продолжить прерванный запуск по README. Зависимости от личного компьютера автора и скрытых ручных настроек должны быть устранены или явно перечислены.

## 25. План реализации и условия завершения этапов

| Этап | Что реализовать | Условие завершения |
|---|---|---|
| 0. Архитектура и окружение | README, инструкции, профили, схемы, doctor, журнал решений | Конфигурация проверяется; зависимости и блокеры видны |
| 1. Исполняемое ядро | CLI, SQLite, задачи, события, artifacts, locks, resume, бюджеты | Прерывание/продолжение и идемпотентность проходят тесты |
| 2. Исследование | HTTP/browser crawl, sitemap, снимки, URL и медиа | Эталонный сайт полностью учтён, ограничения корректно отражены |
| 3. Модель и маршруты | Extractor, типы страниц, источник фактов, route manifest | Сложные URL и сущности проходят независимые проверки |
| 4. Битрикс | Базовый шаблон, модуль, миграции, импорт и админка | Тестовые данные импортированы, редактируются, адреса работают |
| 5. Команда агентов | Реальный Codex-адаптер, роли, обмен результатами, ограничения | Фактический параллельный запуск и повтор после сбоя подтверждены |
| 6. Дизайн и сборка | Токены, компоненты, адаптивные шаблоны, сборка всех страниц | Новая версия работает на целевом Битрикс, не только в HTML-preview |
| 7. QA и демо | Полные проверки адресов, сценарии, отчёты, доступ к демо | DEMO_READY соответствует критериям, дефекты не скрыты |
| 8. Эксплуатация | Package, backup/restore, runbook внедрения и отката | Тестовое восстановление и репетиция переключения подтверждены |
| 9. Пилоты | Услуги, каталог, магазин из разных типов источников | Три отчёта с качеством, временем, расходами и долей ручной работы |

В начале разработки создать маленький сквозной сценарий через этапы 1–4: тестовый источник → данные → маршруты → Битрикс → проверка. После этого расширять покрытие. Не завершать проект на уровне структуры папок, промптов или красивого mockup.

Для каждого этапа: реализованный код, релевантные тесты, фактический запуск, обновлённая документация и сохранённые доказательства. Если окружение для интеграционного теста отсутствует, остальные независимые задачи продолжаются, а соответствующий этап остаётся непроверенным.

Точная стоимость и срок разработки определяются после этапов 0–1 и первого сквозного сценария. Не устанавливать фиктивный срок «за один запуск» для произвольного сайта.

## 26. Что не входит в первую версию

Публичный SaaS, клиентский кабинет, тарифы и платежи Upgrade; массовый поиск клиентов; автоматические письма и звонки; обход защиты сайтов; импорт закрытых данных без доступа; универсальное воспроизведение любого неизвестного серверного алгоритма; автоматическая покупка лицензий; перенос любого сайта без исключений; доказанный рост продаж; массовая синхронизация production-цен без отдельного задания.

Для будущего сервиса предусмотрены расширяемое хранилище, адаптер исполнителей и стабильные контракты ядра. Серверную БД, очередь нескольких хостов, роли сотрудников и веб-интерфейс добавлять при появлении соответствующей потребности.

## 27. Комплект сдачи и определение готовности проекта Upgrade

Исполнитель передаёт:

1. Репозиторий исходного кода с зафиксированными зависимостями.
2. Работающий CLI и фактический адаптер Codex, а не заглушки.
3. Набор ролей и локальных skills с исполняемыми процедурами.
4. Тестовые сайты, эталонные данные и набор приёмочных испытаний.
5. Развёртываемый базовый проект Битрикс с собственным шаблоном и импортёром.
6. Документацию установки, запуска, остановки, восстановления и добавления адаптеров.
7. Матрицу совместимости, отчёт по ограничениям и известным дефектам.
8. Три пилотных проекта с демо и измеренными результатами.
9. Подтверждение изоляции, отсутствия реальных отправок из демо и восстановления из backup.

Проект считается завершённым в согласованной версии, когда оператор из Codex может создать новый проект по URL, получить проверенное демо на Битрикс, остановить и продолжить работу, проверить адреса и увидеть все ограничения без поиска по истории чата.

Проект не считается завершённым, если существует только главная страница, только статическая копия, только описание агентов, только имитационные тесты вместо Битрикс или если обязательные функции показаны работающими без фактической реализации.

## 28. Исходные допущения для начала разработки

Первый вариант — внутренний инструмент одного оператора. Основная работа выполняется из Codex; исходный сайт может быть на любой платформе; целевая платформа всегда Битрикс; режим по умолчанию — защищённое демо.

Конкретный пилотный URL, сервер для демо, лицензию/редакцию Битрикс, допустимый бюджет и источники секретов необходимо указать перед соответствующим внешним запуском. Их отсутствие не мешает разработке ядра, fixtures, контрактов и локальных проверок.

Параметры, которые не определены пользователем, выбирать по этому ТЗ и записывать в журнал решений. Не расширять проект до SaaS и не сводить его к генератору лендингов без отдельного решения.

Официальные ссылки в документе проверены при подготовке ТЗ. Перед реализацией адаптеров повторно проверить документацию установленной версии. Численные лимиты, архитектура, роли и критерии качества выше являются проектными требованиями, а не утверждениями поставщиков о гарантированных возможностях.
