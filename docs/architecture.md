# Архитектура работающей версии

Оператор или Codex вызывает `packages/cli/index.ts`. Оболочка обращается к тем же операциям `Store` и `Pipeline`, которые доступны программно. SQLite — источник истины; JSONL событий — экспорт. State API рассчитан на одного доверенного локального оператора. Доступ ОС к `state/` даёт полномочия оператора; противодействие злонамеренному локальному владельцу файлов не заявляется.

SQLite `BEGIN IMMEDIATE`, WAL и busy timeout сериализуют мутации; запись события и изменения задачи атомарны. Дополнительно запуск имеет одного диспетчера с lease. Pipeline проверяет владельца до сохранения стадии и артефакта, task workers — актуальный lease/fencing token. Task graph создаётся только со ссылками на уже существующие задачи, поэтому цикл нельзя добавить через `createTask`. Изменения входов рекурсивно делают зависимые задачи STALE.

Артефакт сначала записывается во временный файл, публикуется rename и регистрируется с SHA-256. Файлы сохраняются под UUID-версиями. Сбой между файловой публикацией и SQLite может оставить незарегистрированный файл; он не становится принятым результатом и не используется автоматически. Сборка включает hashes контента, URL, дизайн-токенов, кода Битрикс и lock-файла. Release проверяется по привязанному к неизменяемому артефакту хешу manifest и точному списку файлов.

Crawler хранит очередь и снимки отдельно от core SQLite, одним владельцем каталога. Сохраняются все найденные URL и причины исключений/ошибок; `scope-manifest` замораживается после завершённого ограниченного обхода. Неполный обход возвращает PAUSED. Extractor обрабатывает HTML/DOM детерминированно; источники не становятся инструкциями агенту. Origin, request target, canonical и entity ID разделены.

CodexDispatcher резервирует задачи через ядро и запускает документированный `codex exec`. Worker сохраняет schema/prompt/hash/job/events на диске, собирает финальный JSON и usage. Инструменты модели отключены в текущем автоматическом профиле. Поддержка более сильных профилей требует отдельной изоляции и тестов; внутренние API desktop приложения не используются.

PHP-модуль `upgrade.core` и отдельный importer gateway реализуют интерфейс целевого назначения через документированные API Битрикс. Уникальный target key отделён от названия и URL. Gateway сериализует target ownership, пакеты и сверку. Здесь нет подключения к действующему Битрикс: функциональная совместимость должна быть проверена в установленной редакции.

Проверяющий независимо идёт по исходному scope. Отсутствующий маршрут не исчезает из знаменателя. Готовность fail-closed: NOT_RUN не равен PASS. FixtureTarget существует только для воспроизводимого теста неизвестного исхода записи/повтора/конфликтов; он не является заменой Битрикс.

Резервное копирование Upgrade использует SQLite backup API и manifest файлов. Это отличается от backup Битрикс. При переносе состояния пути snapshot/package привязываются к новому корню, а проверка immutable hashes сохраняется. Нельзя смешивать восстановление кода, состояния Upgrade и клиентской БД в одно обещание rollback.
